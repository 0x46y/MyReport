結論から言うと、高額な業務ソフトを自動化するときは、コードを書けるかどうかより先に、どこまで自社で制御できるかを確認した方がよい。

CATIAのようなCAD、AutoCAD、Microsoft製品、ERP、CRM、PLM、業務パッケージのような外部製品は、すでに多くの機能を持っている。一方で、その製品のAPI、ライセンス、データ形式、ベンダーの製品方針に依存するため、自社の都合だけでは進められないことがある。

この記事では、高額な業務ソフトを自動化するときに、ベンダーサポート、ライセンス費用、データ形式、周辺ツール開発、独自システム化、現場の受け入れをどう確認するかを整理する。

API、ライセンス、ベンダーロックイン、STEPなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## ベンダーサポートは万能ではない

高額な業務ソフトでは、保守契約やサポート契約を結んでいることがある。

そのため、困ったことがあればベンダーに問い合わせれば解決できる、と考えたくなる。

もちろん、サポート契約には大きな価値がある。

- 正規の使い方を確認できる
- 既知の不具合や回避策を確認できる
- ライセンスや製品構成を確認できる
- バージョンアップやサポート期限を確認できる
- 公式な回答を社内説明に使える

ただし、サポートは万能ではない。

特に次のような要望は、すぐに解決しないことがある。

- 製品が想定していない自動化
- 公開APIにない内部情報の取得
- 独自の業務フローに合わせた機能追加
- 他社ツールや自作ツールとの特殊な連携
- ライセンス範囲外の形式変換
- 製品ロードマップにない改善要望

ベンダー側から見ると、特定企業だけが必要とする機能をすぐ実装するのは難しい。開発コスト、サポートコスト、品質保証、他機能への影響、他顧客の需要、製品戦略を考える必要があるからだ。

そのため、「高額な製品だから問い合わせれば何とかなる」と考えるのではなく、「サポートで確認できること」と「自社で調査・設計する必要があること」を分けて考えたい。

## 自動化の選択肢を分ける

高額な業務ソフトを自動化するとき、選択肢はいくつかある。

| 方針 | 内容 | 向いているケース | 注意点 |
| --- | --- | --- | --- |
| ベンダー機能を使う | 公式機能、マクロ、API、追加モジュールを使う | 製品の想定範囲に近い処理 | ライセンスやAPI範囲に依存する |
| 周辺ツールを作る | 既存ソフトの入出力を補助するツールを作る | 既存業務を大きく変えずに効率化したい | できる範囲は既存ソフトに左右される |
| 一部だけ高機能ライセンスを使う | 変換や出力だけ専用環境で行う | 全員に高額ライセンスを配ると費用が重い | 運用手順とボトルネックを決める必要がある |
| 中間形式に変換する | STEP、CSV、PDF、画像などに出して別ツールで扱う | 後工程を自社側で制御したい | 変換時に情報が落ちることがある |
| 独自システムへ置き換える | 同じ目的のアプリや管理システムを自作する | 既存製品ではどうしても合わない | 開発、教育、移行、保守が重い |

重要なのは、最初から「全部自作する」か「既存ソフトに全部任せる」かの二択にしないことだ。

現実的には、既存ソフトの強い部分は使い、変換、検査、集計、入力補助、レポート生成など、自社で制御したい部分だけ周辺ツールとして切り出す方が進めやすいことが多い。

## 一部だけ高機能ライセンスを使う選択肢

高額な業務ソフトでは、利用者全員に同じ高機能ライセンスを配ると費用が大きくなる。

一方で、全員がその高機能を毎日使うとは限らない。

たとえばCADで考えると、通常の閲覧や簡単な操作は標準ライセンスで足りるが、STEP変換や高度なデータ出力だけ高機能ライセンスが必要になることがある。

この場合、次のような運用も候補になる。

1. 一部の端末や部署だけ高機能ライセンスを持つ
2. そこで必要な変換や出力を行う
3. 変換後のSTEPや中間形式を別ツールで扱う
4. 後工程の検査、シミュレーション、集計、表示は自作ツールや別サービスで行う

この方法なら、全員分の高額ライセンスを増やさずに、必要な変換だけを集中的に処理できる可能性がある。

ただし、これも万能ではない。

- 高機能ライセンスを持つ端末がボトルネックになる
- 変換待ちが発生する
- 誰が変換を実行するか決める必要がある
- 変換後に情報が落ちる可能性がある
- 中間形式で品質確認する必要がある
- ライセンス上その使い方が許されるか確認する必要がある

費用を抑えるための工夫は、運用手順や責任範囲とセットで考えたい。

## 中間形式に出すと自由度は増えるが情報は落ちる

商用ソフトのネイティブ形式を直接扱えない場合、STEP、IGES、STL、CSV、PDF、画像などの中間形式へ出力して、別ツールで扱う方法がある。

これはかなり有効なことがある。

たとえば、CATIAのネイティブデータを直接解析できなくても、STEPへ変換できれば、OCCTのようなライブラリや別の3Dツールで形状を読み込める可能性がある。

一方で、中間形式には限界がある。

- 設計履歴が落ちる
- パラメータが落ちる
- 属性情報が落ちる
- アセンブリ構造が変わる
- 曲面やソリッド性が変わる
- 出力設定やライセンスで結果が変わる

つまり、中間形式は「依存関係を弱める手段」にはなるが、「元データと同じ情報をすべて保持する手段」とは限らない。

この点は [CATPart、STL、IGES、STEPは何が違うのか](/reports/cad-file-formats-native-stl-iges-step) にも整理している。

## 独自システムで置き換える前に現場の負担を見る

既存ソフトの制約が大きいと、同じような機能を自社で作ればよいのではないか、という話になることがある。

技術的には選択肢としてあり得る。

しかし、既存ソフトを置き換える場合、実装だけでは済まない。

- 既存ソフトの高度な機能を再現できるか
- 既存データを移行できるか
- 現場が新しい操作を覚えられるか
- 現場の入力作業が増えないか
- 既存の業務フローを壊さないか
- 本当に現場の負担が減るのか
- 保守担当を社内で持てるか

管理側から見ると、新システムによってデータを集めやすくなる、標準化しやすくなる、進捗を見える化しやすくなる、という利点がある。

一方で、現場側から見ると、入力項目が増えた、操作を覚える必要がある、今までの手順が変わった、余計な確認が増えた、と感じることがある。

ここを軽く見ると、「技術的には作れたが、現場で使われない」状態になりやすい。

独自システム化を検討するなら、「管理側が便利になる」だけでなく、「現場の負担がどう減るか」を説明できる必要がある。

## 何を自社で制御したいのかを先に決める

高額な業務ソフトの自動化では、最初に「何を自社で制御したいのか」を決めたい。

たとえば、次のように分けて考える。

| 制御したいこと | 確認したいこと |
| --- | --- |
| データ入力 | 既存ソフトの画面で入力するのか、自社ツールで入力するのか |
| データ変換 | 公式機能で出すのか、別ツールで変換するのか |
| 検査 | 商用ソフト内で確認するのか、自作ツールで自動検査するのか |
| 解析 | ネイティブ形式のまま解析するのか、中間形式で解析するのか |
| レポート | 既存ソフトの出力を使うのか、自社で生成するのか |
| 権限 | 商用ソフトの権限に乗るのか、別システムで管理するのか |
| 保守 | ベンダーに依頼するのか、自社で保守するのか |

すべてを自社で制御しようとすると重くなる。

逆に、すべてをベンダー製品に任せると、自社の都合で変えにくい。

そのため、どのレイヤーまで自社で持つのか、どこから外部製品に任せるのかを決めることが重要になる。

この点は [製造業の3D自動化で難しいのは、3D表示ではなくCADの中身を制御すること](/reports/manufacturing-3d-automation-cad-control) とも関係する。

## 小さな検証で確認したいこと

高額な業務ソフトの自動化では、最初から大きな開発に入るより、小さな検証で確認した方がよい。

確認したいことは次のようなものだ。

| 観点 | 確認したいこと |
| --- | --- |
| API | 必要な情報を取得できるか |
| ライセンス | 自動化、変換、出力が契約上許されるか |
| データ形式 | ネイティブ形式、中間形式、出力形式で何が残るか |
| 変換品質 | STEPやCSVなどに出したときに情報が落ちないか |
| 運用 | 誰が実行し、誰が確認するか |
| 費用 | 全員分のライセンスが必要か、一部でよいか |
| 現場負担 | 新しい操作や入力が増えすぎないか |
| 代替案 | できない場合に、手動工程、範囲縮小、別ツールで逃げられるか |

この検証で「できる範囲」と「できない範囲」を分ける。

できないことが見つかるのは失敗ではない。大きく作る前に、依存先の制約や費用、運用上の問題が見えたという意味では、技術調査の成果になる。

この考え方は [技術調査で撤退条件を決める意味](/reports/technical-research-exit-criteria) ともつながる。

## まとめ

高額な業務ソフトを自動化するときは、コードを書けるかだけで判断しない方がよい。

ベンダーサポートがあっても、製品が想定していない使い方や独自連携まで必ず対応してもらえるとは限らない。ライセンス、API、データ形式、製品ロードマップ、現場運用の制約を先に確認する必要がある。

現実的には、既存ソフトをすぐ置き換えるのではなく、既存ソフトの強い部分は使いながら、変換、検査、集計、入力補助、レポート生成のような周辺機能を自社で持つ方が進めやすいことが多い。

重要なのは、何を自社で制御したいのかを先に決めることだ。

そのうえで、ライセンス費用、ベンダー依存、現場負担、代替案を含めて、小さく検証しながら判断したい。

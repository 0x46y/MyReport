結論から言うと、技術的にできることと、会社として採用できることは別である。

AIでコードを書ける。APIがある。クラウドで動く。OSSで実装できる。小さな検証では成功した。これらは重要な判断材料になる。

しかし、会社として採用するには、保守担当、責任範囲、費用、ライセンス、教育、現場の受け入れ、障害時対応、既存業務との整合性まで含めて成立する必要がある。

この記事では、「技術的には可能」と「会社として採用してよい」の間にある差を整理する。

PoC、ライセンス、責任分界点、非機能要件などの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 技術的にできることは出発点でしかない

技術調査では、まず「できるか」を確認する。

たとえば、次のような確認だ。

- AIで要約や分類ができるか
- Cloudflare Workersで動くか
- ExcelのデータをDBへ取り込めるか
- 商用ソフトのAPIから必要な情報を取得できるか
- STEPやCSVのような中間形式に変換できるか
- 管理画面を作れるか

これらは重要だ。

できないものは採用できない。

しかし、できることが分かっただけでは、採用判断としてはまだ足りない。

たとえば、AIで分類できても、誤分類したときに誰が確認するのかが決まっていなければ業務に入れにくい。クラウドで動いても、月額費用や障害時対応を説明できなければ継続運用しにくい。商用ソフトのAPIで一部の処理ができても、ライセンスや現場操作の変更が重ければ採用しにくい。

技術的にできることは、採用判断の出発点であって、ゴールではない。

## 会社として採用するには別の条件がある

会社として採用するには、技術以外の条件も見る必要がある。

| 観点 | 確認したいこと |
| --- | --- |
| 費用 | 初期費用、月額費用、ライセンス費、運用費を説明できるか |
| 保守 | 担当者が変わっても維持できるか |
| 責任 | データ、判断、障害、問い合わせの責任範囲が明確か |
| 教育 | 現場が新しい操作を覚えられるか |
| 既存業務 | 今の業務フローと衝突しないか |
| セキュリティ | 権限、機密情報、外部送信を管理できるか |
| ライセンス | 商用利用、自動化、外部連携が許可されるか |
| 代替手段 | 止まったときに手動運用や別案へ逃げられるか |

この表のどれか一つでも未整理だと、技術的には動いていても会社としては採用しにくくなる。

採用とは、単に「動くものを入れること」ではない。

組織として、費用を払い、責任を持ち、使い続けられる状態にすることだ。

## AIなら作れることと、AIを業務に入れることは違う

AIを使うと、画面、CRUD、API、テスト、ドキュメント、簡単な管理画面はかなり速く作れるようになっている。

しかし、AIが作れることと、会社としてAIを業務に入れてよいことは別だ。

確認したいこと:

- AIの出力を誰が確認するか
- 間違った出力が出たとき誰が修正するか
- 入力データを外部AIサービスへ送ってよいか
- AIが使った情報源を追えるか
- 費用が利用量に応じて増えたとき許容できるか
- 業務上の正解を人間が定義できるか

AIは候補を出せる。

しかし、その候補を採用するかどうかは、業務側、管理側、運用側が判断する必要がある。

この点は [AIがコードを書く時代に人間は何を確認するのか](/reports/ai-code-generation-human-checkpoints) や [AIに専門業務を教える前に確認したい学習データの問題](/reports/ai-training-data-for-specialized-work) とも関係する。

## 現場が使うかどうかは技術だけでは決まらない

新しいシステムを作ると、管理側には便利に見えることがある。

- データが集まる
- 進捗が見える
- 標準化できる
- 集計しやすい
- 履歴を残せる

しかし現場側から見ると、別の負担が増えることもある。

- 入力項目が増えた
- 今までのExcelより時間がかかる
- 承認待ちが増えた
- 例外処理がやりにくい
- 使い慣れた業務ソフトから離れる必要がある
- トラブル時に誰へ連絡すればよいか分からない

技術的には正しい設計でも、現場の負担が増えるだけなら使われにくい。

会社として採用するには、「管理側が便利になる」だけでなく、「現場の作業がどう軽くなるのか」も説明したい。

この点は [高額な業務ソフトを自動化するときに確認したいこと](/reports/expensive-business-software-automation-checkpoints) ともつながる。

## Excelやスプレッドシートが残る理由もここにある

技術的には、ExcelやスプレッドシートをDBや管理画面に置き換えることはできる。

しかし、それが常に会社として良い判断とは限らない。

Excelやスプレッドシートには、次のような強みがある。

- 現場が自分で直せる
- 導入が早い
- 追加費用が少ない
- 表として見やすい
- 自由にメモや説明を入れられる
- システム化前の試作品として使える

一方で、外部公開、権限管理、履歴、承認、復旧、データ連携が必要になると、表形式の自由度がリスクになる。

つまり、判断すべきなのは「Excelは古いか」ではない。

今の業務規模ではExcelで十分なのか、それとも会社として管理画面やDBを持つ必要があるのか、ということだ。

この点は [業務システムでExcelやスプレッドシートがなくならない理由](/reports/why-excel-spreadsheets-remain-business-systems) と関係する。

## 採用できない理由が分かることも成果になる

技術調査では、採用できない理由が分かることも成果になる。

たとえば、次のような結果が出ることがある。

- 技術的には可能だが、ライセンス費用が合わない
- 小さな検証では動くが、本番データ量では性能が足りない
- AIの精度は出るが、確認者を置けない
- 管理画面は作れるが、現場の入力負担が増える
- 外部APIは便利だが、停止時の代替手段がない
- OSSで作れるが、社内に保守できる人がいない

これは「失敗」ではない。

会社として採用する条件を満たしていないことが分かった、という判断材料である。

むしろ、この段階で分かれば、予算を大きく使う前に方向転換できる。

この点は [技術調査で撤退条件を決める意味](/reports/technical-research-exit-criteria) ともつながる。

## 採用判断で見たいこと

技術的にできることを会社として採用する前に、少なくとも次の点を確認したい。

| 観点 | 確認したいこと |
| --- | --- |
| 目的 | 何を改善するために採用するのか |
| 利用者 | 誰が使い、誰が判断するのか |
| 業務負荷 | 現場の作業は減るのか、増えるのか |
| データ責任 | 登録、確認、承認、修正、復旧を誰が持つのか |
| 費用 | 初期費用、月額費用、運用人件費を含めて成立するか |
| 保守 | 担当者が変わっても維持できるか |
| 権限 | 誰が見てよく、誰が編集してよいか |
| 障害時 | 止まったときの代替手段があるか |
| 契約 | ライセンス、利用規約、外部送信が問題ないか |
| 撤退 | やめる条件や別案へ切り替える条件があるか |

この表は、採用を止めるためのものではない。

採用するなら、どの条件を満たせばよいかを明確にするためのものだ。

## 技術者が説明したいこと

技術者は、「できます」だけでなく、「どの条件なら採用できます」と説明できると話が進みやすい。

たとえば、次のように整理する。

```text
技術的には可能です。

ただし、会社として採用するには次の条件を確認したいです。

- 月額費用が予算内に収まる
- データ確認者が決まっている
- 障害時の手動運用がある
- ライセンス上その使い方が許可されている
- 現場の入力負担が増えすぎない

これらを満たせるなら採用候補になります。
満たせない場合は、範囲縮小や別案を検討した方がよいです。
```

この言い方なら、「できない」と切り捨てるのではなく、採用条件を整理できる。

発注側や管理側にとっても、何を決めれば進められるのかが見えやすくなる。

## まとめ

技術的にできることと、会社として採用できることは違う。

AIで作れる。クラウドで動く。APIがある。OSSで実装できる。小さな検証で成功した。これらは重要な材料だ。

しかし会社として採用するには、費用、保守、責任範囲、教育、現場の受け入れ、障害時対応、ライセンス、撤退条件まで含めて考える必要がある。

技術調査の価値は、できるかどうかを調べることだけではない。

どの条件なら採用できるのか、どの条件なら保留や別案にするのかを明確にすることにもある。

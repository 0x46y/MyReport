結論から言うと、静的サイトをすぐにCMS化する前に、今の運用で得ているメリットと、CMS化によって増える運用コストを分けて考えたい。

CMS化すると、記事の追加、画像の貼り付け、下書き管理、公開フローは楽になることがある。一方で、Gitで管理しているMarkdown記事をDBや外部サービスへ移すと、差分確認、AIによる記事全体の読み取り、ローカルでの一括編集、デプロイの単純さを失う可能性もある。

この記事では、静的サイトをCMS化する前に確認したいことを、技術記事サイトやナレッジサイトの運用目線で整理する。

CMS、CRUD、DB、認証などの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 静的サイトには静的サイトの強みがある

静的サイトは、記事やページをビルド時にHTMLとして生成し、公開先へ配信する構成だ。

更新のたびにビルドやデプロイは必要になるが、記事サイトやポートフォリオのように、読むことが中心のサイトでは相性がよい。

静的サイトの強みは次のような点にある。

| 観点   | 静的サイトの強み                                               |
| ------ | -------------------------------------------------------------- |
| 費用   | サーバーを常時動かさずに済み、低コストで運用しやすい           |
| 速度   | 生成済みのページを配信するため、表示が安定しやすい             |
| 管理   | MarkdownやコードをGitで管理できる                              |
| 差分   | どの記事をどう変更したか、履歴を確認しやすい                   |
| AI編集 | CodexやClaude CodeのようなAIに、記事ファイル全体を読ませやすい |
| 移行   | ファイルとして残るため、別の仕組みへ移しやすい                 |

特に技術記事や調査記録では、記事そのものが判断材料になる。

そのため、記事本文がファイルとして残り、検索でき、差分を追えることは大きい。

## CMS化で得られるもの

一方で、CMS化にも明確なメリットがある。

CMSは、記事、画像、カテゴリ、タグ、公開状態などを管理するための仕組みだ。

管理画面があると、次のような作業は楽になりやすい。

- ブラウザから記事を作成する
- 画像をドラッグアンドドロップで追加する
- 下書きと公開を切り替える
- カテゴリやタグを画面から選ぶ
- 複数人で記事を編集する
- 公開前にレビューする
- 技術者以外の人が更新する

発注者や運用担当者が直接更新するサイトなら、CMSの価値は高い。

たとえば、施設情報、製品情報、FAQ、事例紹介、採用情報のように、日常的に非エンジニアが更新する情報は、管理画面がある方が運用しやすい場合がある。

## CMS化で失うものもある

CMS化は「管理画面が付くから便利」というだけではない。

構成を変えることで、これまで簡単だったことが難しくなる場合もある。

| 失う可能性があるもの | 何が起きるか                                                             |
| -------------------- | ------------------------------------------------------------------------ |
| Git管理              | 記事本文がDBや外部サービスに移り、変更履歴をコードと一緒に追いにくくなる |
| AIによる一括編集     | AIがローカルファイルをまとめて読めず、API経由の取得が必要になる          |
| ローカル編集         | エディタで複数記事を一括検索・置換しにくくなる                           |
| 構造変更の自由度     | DBスキーマやCMS側のモデル変更が必要になる                                |
| デプロイの単純さ     | CMS、API、認証、DB、画像ストレージなど管理対象が増える                   |
| 費用の読みやすさ     | DB、ストレージ、画像配信、認証、管理画面の運用費が増える                 |

特にAIと一緒に記事を整理している場合、Markdownファイルがローカルにあることはかなり強い。

AIは、記事本文、ロードマップ、用語集、AGENTS.mdを同時に読みながら、文体、重複、リンク、用語の使い方を調整できる。

記事がCMSのDBに入ると、AIが全体像を把握するにはAPI接続、エクスポート、同期処理が必要になる。これはできないわけではないが、静的サイトより仕組みは複雑になる。

## 先に困っている作業を分ける

CMS化を考える前に、まず何に困っているのかを分けたい。

同じ「更新が面倒」でも、原因は複数ある。

| 困っていること                  | 代替案                                     |
| ------------------------------- | ------------------------------------------ |
| 画像を貼るのが面倒              | 画像アップロードだけ補助ツール化する       |
| 記事のfrontmatterを書くのが面倒 | 記事作成テンプレートや生成スクリプトを作る |
| タグやカテゴリが揺れる          | 用語集やタグ一覧を整備する                 |
| ロードマップ追加を忘れる        | 記事作成時にロードマップ候補を表示する     |
| 公開前レビューが必要            | Pull Requestや下書きブランチで管理する     |
| 非エンジニアが更新したい        | CMSや管理画面を検討する                    |
| 複数人で同時編集したい          | CMS、Notion、GitHub連携などを検討する      |

すべてをCMS化しなくても、困っている部分だけを補助ツールにする方法もある。

たとえば、記事本文はMarkdownのままにして、画像管理だけを支援する。あるいは、記事作成時のテンプレート生成だけを自動化する。

このように分けると、「CMSを導入するかどうか」ではなく、「どの運用課題をどの手段で軽くするか」として判断しやすくなる。

## CMSは本番置き換えではなく試作品として作る方法もある

CMS型の管理画面を作る価値はある。

ただし、それをすぐ本番サイトへ置き換える必要はない。

まずは別の試作品として、次のような範囲で作る方法がある。

- 記事の一覧を表示する
- 新規記事のfrontmatterを作る
- カテゴリやタグを選ぶ
- 関連記事候補を表示する
- ロードマップの追加候補を出す
- 画像を保存し、Markdownに貼るパスを生成する
- 下書き状態の記事を確認する

この段階では、記事本文をDBへ完全移行しなくてもよい。

Markdownファイルを維持したまま、周辺作業だけを管理画面で助ける構成も考えられる。

これなら、静的サイトの強みであるGit管理とAI編集を残しつつ、運用で面倒な部分だけを軽くできる。

## 非エンジニアが更新できることと安全性は別問題

CMS化を考える理由の一つに、現場担当者が自分で情報を更新したいという要望がある。

たとえば、施設情報、顧客情報、店舗情報、製品情報のようなデータでは、エンジニアへ毎回依頼せず、担当者が好きなタイミングで追加、修正、削除したいことがある。

これは単に「開発者に頼むのが面倒」という話だけではない。更新を依頼する側も、都度エンジニアの作業時間を取らせたくない、細かい修正で相手を振り回したくない、という気遣いを持っている場合がある。

このとき、Googleスプレッドシート、Excel、CSVのような表形式のファイルを、簡易的な管理画面の代わりに使う案が出ることがある。

表であれば非エンジニアにも扱いやすく、最初の試作品としてはかなり有効だ。列を決めて、そこへデータを入力してもらい、サイト側で読み込む構成にすれば、管理画面を作らずに更新フローを試せる。

ただし、更新しやすさと安全性は別問題だ。

たとえば、次のようなことが起きると、システム側の処理に影響する場合がある。

- 空行が途中に入る
- 必須項目が空欄になる
- 列名や列順が変わる
- 想定外の文字や改行が入る
- 削除してはいけない行が消える
- 同じデータが重複して登録される
- 表示用の文字と内部処理用の値が混ざる

内部向けの小さなツールなら、多少の手作業修正で済むこともある。

一方で、外部の利用者が見るサイトや、業務上止まると困る情報では、スプレッドシートの入力ミスがそのまま障害のように見えてしまう可能性がある。

一方で、すべてのケースで最初から専用の管理画面が必要とは限らない。更新頻度が低く、利用者が少なく、データ量も少ない場合は、スプレッドシートやCSVでも十分運用できることがある。

重要なのは、管理画面を作ること自体ではない。運用上の問題を減らし、必要な人が安全に更新できる状態を作ることだ。

そのため、現場が自由に更新できることと、データ構造を安全に保つことの両方を考えたい。

専用の管理画面を作る価値は、見た目を整えることだけではない。必須項目のチェック、入力形式の制限、削除確認、権限管理、変更履歴、公開前確認のように、壊れにくい更新手順を用意できる点にもある。

## CMS化が向いている場合

CMS化が向いているのは、次のような場合だ。

- 技術者以外が日常的に更新する
- 複数人で編集や承認を行う
- 記事よりも施設情報や商品情報のような構造化データが中心
- 管理画面から入力した方がミスを減らせる
- 画像や添付ファイルを頻繁に扱う
- 公開予約、権限管理、レビューが必要
- GitやMarkdownを使わない運用担当者がいる

この場合は、CMS化によって更新負荷を下げられる可能性がある。

ただし、CMS化しても、データ設計、権限管理、バックアップ、運用担当、費用、移行手順は別途考える必要がある。

## 静的サイトのままが向いている場合

一方で、静的サイトのままが向いている場合もある。

- 更新者が主に開発者本人
- MarkdownやGitで管理したい
- 記事本文をAIにまとめて読ませたい
- 変更履歴をコードと一緒に管理したい
- 公開コストを抑えたい
- DBや認証を増やしたくない
- サイト構造を頻繁に変えたい
- 記事が技術調査や意思決定の記録になっている

このような場合、CMS化は便利になる一方で、管理対象を増やすことにもなる。

特に個人サイトや技術調査サイトでは、静的サイトの単純さが運用上の強みになる。

## 確認したいこと

静的サイトをCMS化する前に、少なくとも次の点を確認したい。

| 観点         | 確認したいこと                                  |
| ------------ | ----------------------------------------------- |
| 更新者       | 誰が記事やデータを更新するのか                  |
| 更新頻度     | どれくらい頻繁に更新するのか                    |
| 変更履歴     | Gitで履歴を残す必要があるか                     |
| AI編集       | AIに記事全体を読ませて編集したいか              |
| 画像管理     | 画像や添付ファイルがどれくらい多いか            |
| 権限管理     | 複数人で権限を分ける必要があるか                |
| 費用         | DB、ストレージ、認証、APIの運用費を許容できるか |
| 移行         | 将来、別のCMSや静的サイトへ戻せるか             |
| バックアップ | 記事本文と画像をどう復元するか                  |

この確認をせずにCMS化すると、更新は楽になっても、別の運用負荷が増えることがある。

## まとめ

CMS化は、静的サイトの上位互換ではない。

管理画面があると更新しやすくなる一方で、Git管理、AI編集、差分確認、低コスト運用、構成の単純さを失う可能性がある。

そのため、静的サイトをCMS化する前に、まず何が面倒なのかを分けたい。

記事本文の管理が問題なのか、画像管理が問題なのか、タグ管理が問題なのか、非エンジニアの更新が必要なのかで、選ぶ手段は変わる。

個人の技術記事サイトや調査記録サイトなら、MarkdownとGitを維持したまま、画像管理、テンプレート生成、ロードマップ追加のような周辺作業だけを補助する選択肢もある。

CMS化するかどうかは、管理画面を作れるかではなく、今の運用で得ている強みを失ってもよいかを確認してから判断したい。

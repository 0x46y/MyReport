結論から言うと、日本語データを扱うシステム開発では、文字コードだけでなく、CSV、Excel、旧字、外部システム連携、本番データに含まれる例外ケースまで含めて確認した方がよい。

英数字だけを扱うシステムでは見えにくいが、日本語では「文字数」と「バイト数」が一致しないことがある。さらに、UTF-8、Shift_JIS、Windowsのコードページ、BOM有無、Excelの読み込み方が絡むと、同じデータでも環境によって文字化けや欠落が起こる。

この記事では、文字コードの厳密な歴史ではなく、業務システムや自動化で日本語データを扱うときに確認したいことを整理する。

特に注意したいのは、開発中の少量データでは問題が見つからなくても、本番に近い大量データを扱ったときに旧字、長い住所、Excel由来のCSV、外部システム由来の文字が混ざって発覚する場合があることだ。

UTF-8、Shift_JIS、BOM、CSV、コードページ、環境依存文字などの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 文字数とバイト数は同じではない

昔のシステムやC言語に近い処理では、文字列を「何バイトか」で扱う場面がある。

英数字だけなら、1文字を1バイトとして扱える場面が多い。しかし日本語では、文字コードによって1文字が2バイト、3バイト、またはそれ以上になることがある。

たとえば、Shift_JISでは英数字が1バイト、日本語の多くが2バイトで表現される。一方、UTF-8では英数字は1バイトだが、日本語の多くは3バイトになる。

ここで問題になるのは、「10文字まで入る」と「10バイトまで入る」が同じではないことだ。

たとえば `AAAAAAAAAA` は10文字で、英数字だけなら10バイト程度で収まる。一方で「東京都千代田区」は7文字だが、UTF-8では日本語1文字が複数バイトになるため、英数字7文字と同じサイズでは扱えない。

発注側や利用者から見ると、どちらも「数文字の文字列」に見える。しかしシステム内部では、英数字なら入る長さでも、日本語では途中で切れることがある。

特に古いシステムや外部連携では、画面上は「20文字まで」と見えていても、内部的には「20バイトまで」で作られていることがある。その場合、英数字なら20文字入るが、日本語では10文字前後で制限に当たる場合がある。

確認したいこと:

- その項目は文字数で制限しているのか、バイト数で制限しているのか
- 既存DBや外部システムの桁数制限は何を基準にしているのか
- 途中で文字列を切り詰める処理がないか
- 日本語の途中でバイト列を切って文字化けしないか
- 入力、保存、出力で同じ文字コードを使っているか

日本語データを扱う場合、単に「文字列」と考えるのではなく、「どの文字コードで、どの単位で制限しているか」を確認したい。

## レガシーシステムではShift_JISやコードページが残りやすい

古い業務システム、Windows向けツール、バッチ処理、Excel連携では、UTF-8ではなくShift_JIS系の文字コードが前提になっていることがある。

特にWindowsでは、Shift_JISに近いが完全に同じではないコードページが使われることがある。日本語環境では、CP932やWindows-31Jと呼ばれる文字セットが関係することがある。

ここで問題になるのは、開発側がUTF-8で作ったデータを、古いシステムやExcelがShift_JIS系として読んでしまうことだ。

確認したいこと:

- 連携先はUTF-8を受け取れるか
- Shift_JIS、CP932、Windows-31Jのどれを想定しているか
- 文字コードを明示する設定があるか
- 変換できない文字が出たときにエラーにするか、置換するか
- 置換された文字をログや検査で検出できるか

文字化けは、コードのロジックが間違っていなくても発生する。入力側と出力側で「同じ文字として扱っているつもり」でも、文字コードの前提が違うと壊れる。

## 旧字や環境依存文字は業務データで問題になりやすい

人名、住所、組織名、施設名では、旧字や環境依存文字が出てくることがある。

たとえば「高橋」の「高」が、一般的な「高」ではなく「髙」のような字で登録されている場合がある。「﨑」や「𠮷」のように、氏名で見かける字が外部システムやCSV変換で問題になることもある。ほかにも、旧字体、異体字、丸数字、ローマ数字、機種依存文字、全角記号が混ざることがある。

UTF-8自体は多くの文字を扱えるが、途中でShift_JIS系へ変換したり、古いDB、古いCSV取り込み、特定フォント、外部システムの制限を通したりすると、文字が `?` や空文字に置き換わることがある。

確認したいこと:

- 人名、住所、施設名に旧字や異体字が入る可能性があるか
- その文字をDB、CSV、Excel、外部システムが保持できるか
- 変換できない文字をどう検出するか
- 表示できるフォントがあるか
- 同じ人物や施設を、旧字と新字で別データとして扱わないか
- 検索では旧字と新字を同一視する必要があるか

旧字の問題は、単なる文字化けではなく、本人確認、名簿、請求、医療、自治体、金融、教育のような業務で重要になることがある。見た目が少し違うだけに見えても、業務上は別の文字として扱われる場合がある。

## CSVとExcelではBOM有無が問題になりやすい

CSVはテキストファイルなので扱いやすい一方、Excelで開くときに文字コードの問題が起きやすい。

特に、ユーザーがCSVファイルをダブルクリックしてExcelで開く運用では、UTF-8のCSVが文字化けすることがある。環境によっては、UTF-8 BOM付きのCSVにするとExcelがUTF-8として認識しやすくなる。

一方で、システム同士の連携やプログラムで読み込むCSVでは、BOMなしUTF-8を前提にしていることも多い。BOMがあると、先頭列名の前に見えない文字が混ざり、`id` ではなく `\ufeffid` のように扱われてしまうことがある。

確認したいこと:

| 用途 | 確認したいこと |
| --- | --- |
| ユーザーがExcelで開くCSV | BOM付きUTF-8やExcel向け出力が必要か |
| システムが読み込むCSV | BOMなしUTF-8、Shift_JIS、区切り文字、改行コードの前提 |
| 外部システム連携 | 仕様書で指定された文字コードと改行コード |
| Excelから保存し直すCSV | 文字コードや日付形式が変わらないか |
| 自動処理 | 先頭列名にBOMが混ざっていないか |

BOMは、ファイルの先頭に付く目印のような情報だ。もともとは文字のバイト順を示すために使われる考え方だが、UTF-8ではExcelなどに文字コードを認識させる目印として扱われることがある。だから「BOM付きが正しい」「BOMなしが正しい」と一律には決めにくい。

重要なのは、誰がそのCSVを開くのか、どのアプリが読むのか、どのシステムへ渡すのかを先に決めることだ。

## バッチ処理やターミナルでは表示だけ文字化けすることがある

Windowsのバッチファイル、PowerShell、コマンドプロンプト、ターミナル、ログ出力では、日本語メッセージが文字化けすることがある。

ここで厄介なのは、データ自体が壊れているのか、表示だけが壊れているのかを分ける必要があることだ。

たとえば、自分で出したエラーメッセージが文字化けする場合もあれば、別アプリを自動操作して取得した文字列が途中で文字化けする場合もある。標準出力、標準エラー、ファイル出力、ログビューア、Excel、テキストエディタで見え方が変わることもある。

確認したいこと:

- 実行するターミナルの文字コードは何か
- バッチファイル自体の保存形式は何か
- 標準出力とファイル出力で文字化けの状態が違うか
- 外部アプリから取得した文字列の文字コードは何か
- ログファイルをどのツールで開く前提か
- エラー時に文字化けしても原因を追えるログが残るか

文字化けが起きたときは、すぐに「データが壊れた」と判断せず、表示、保存、変換、連携のどこで問題が起きているかを分けて見る必要がある。

## C言語や古い処理では文字列操作が難しくなりやすい

C言語に近い低レイヤーの処理では、文字列をバイト列として扱う場面が多い。

これは高速で細かく制御できる一方、文字コード、終端文字、バッファサイズ、メモリ確保、文字列切り出しを開発者が意識する必要がある。

バッファは、文字列を一時的に入れておく入れ物のようなものだ。たとえば「名前を20バイト分だけ入れる箱」を用意している場合、英数字なら20文字入るが、日本語では10文字程度しか入らない場合がある。

ここを「20文字入る」と誤解すると、日本語だけ途中で切れたり、文字の途中で切れて文字化けしたり、古い処理では後ろのデータに影響したりすることがある。

日本語が混ざると、次のような問題が起きやすい。

- 文字の途中で切り詰めてしまう
- バッファサイズをバイト数で見積もり間違える
- 1文字ずつ処理しているつもりが、実際には1バイトずつ処理している
- Shift_JISの2バイト目を別の文字として扱ってしまう
- UTF-8のマルチバイト文字を途中で分割してしまう

Rust、Go、Python、JavaScriptなどの言語では、標準ライブラリや文字列処理の仕組みにより、UnicodeやUTF-8を扱いやすくなっている。ただし、それでも外部ファイル、CSV、Excel、DB、Windows API、古い外部システムとつなぐ場合は、文字コードの境界を確認する必要がある。

つまり、現代の言語を使えばすべて解決するわけではない。どこでUTF-8として扱い、どこでShift_JISやWindowsコードページへ変換するのかを決める必要がある。

## 開発時に確認したいこと

日本語データを扱うシステムでは、最初に次の点を確認したい。

| 観点 | 確認すること |
| --- | --- |
| 入力 | どの文字コードで入ってくるか |
| 保存 | DBやファイルで旧字や記号を保持できるか |
| 出力 | CSV、Excel、PDF、ログで文字化けしないか |
| 変換 | UTF-8、Shift_JIS、CP932のどこを通るか |
| 表示 | ブラウザ、Excel、ターミナル、テキストエディタで見え方が違わないか |
| 検索 | 旧字、新字、全角半角、大小文字をどう扱うか |
| エラー | 変換できない文字を検出できるか |
| 運用 | 利用者がどのアプリでファイルを開くか |

特に、次のような機能では早めに確認したい。

- CSV出力
- Excel連携
- 名簿や顧客データの取り込み
- 住所や施設名の検索
- バッチ処理
- 外部システム連携
- ログ出力
- 旧システムからのデータ移行

## 小さな検証だけでは見つからないこと

日本語データの問題は、実装の最後にまとめて直すより、早い段階で小さく確認した方がよい。

たとえば、次のようなテストデータを先に用意する。

- ひらがな、カタカナ、漢字
- 全角英数字と半角英数字
- 記号、括弧、波ダッシュ、ハイフン
- 旧字や異体字を含む氏名
- 長い住所
- カンマや改行を含むCSV項目
- 先頭列名つきCSV
- Excelで開くためのCSV
- バッチ処理やログに出す日本語メッセージ

最初から全ケースを完璧に網羅する必要はない。ただし、日本語データを扱うことが分かっているなら、代表的な文字化けケースを小さく試しておくと、後からの修正範囲を減らしやすい。

一方で、小さな検証だけで十分とは限らない。

開発中は数百件や数千件のテストデータでは問題が見つからなくても、実際の業務データを大量に扱ったときに初めて発覚することがある。たとえば、数十万件の名簿や施設データを取り込んだときに、少数の旧字、長い住所、外部システム由来の特殊文字、想定外の改行やカンマが混ざっていることがある。

この場合、小さな検証は「方向性を確認するため」のものだと考えたい。小さな検証で問題が見つからなかったとしても、本番に近いデータ量や実データに近いサンプルで再確認する必要がある。

確認したいこと:

- 開発用データだけでなく、本番に近いデータでも試しているか
- 旧字、長い住所、特殊記号を含むレコードが混ざっていないか
- 文字化けや変換失敗を全件チェックできるログがあるか
- 少数の異常データだけが処理全体を止めないか
- 変換できないデータを手動確認へ回せるか

これは負荷テストとは少し違う。負荷テストは主に処理速度やサーバー負荷を見る。一方で、ここで見たいのは「大量の実データに混ざる例外文字を見つけられるか」だ。

この考え方は [小さな検証（PoC）が成功しても本番導入できない理由](/reports/poc-success-production-adoption-risks) ともつながる。代表データだけで動いたとしても、旧字、CSV、Excel、外部連携を通したときに本番導入できるとは限らない。

## 日本語環境は海外記事だけでは解決しにくいことがある

システム開発の情報は英語圏のドキュメントや記事が多い。

もちろん、公式ドキュメントや英語圏の記事は重要だ。ただし、日本語を扱う業務システムでは、海外記事だけでは同じ問題にたどり着きにくいことがある。

たとえば、次のような問題は日本語環境の事情が強い。

- Shift_JISやCP932
- Excelで開くCSV
- UTF-8 BOM付きCSV
- 旧字や異体字を含む氏名
- 日本語Windowsのコードページ
- バッチ処理やターミナルの日本語文字化け
- 戸籍、医療、自治体、教育、金融などで使われる表記の厳密さ

海外記事で見つかる一般的な文字列処理の説明が技術的に正しくても、日本の業務データやExcel運用では別の問題が出ることがある。

そのため、日本語環境で使うシステムでは、海外記事やライブラリの説明だけで判断せず、実際の日本語データ、Excel、CSV、Windows環境、外部連携を通して確認したい。

## まとめ

日本語データを扱うシステム開発では、文字コード、CSV、Excel、旧字、Windowsコードページ、バッチ処理の表示差分、実データに含まれる例外ケースが問題になりやすい。

重要なのは、UTF-8やShift_JISの定義を暗記することではない。

どの入力が来るのか、どこに保存するのか、誰がどのアプリで開くのか、どの外部システムへ渡すのか、変換できない文字をどう検出するのか、本番に近いデータでどこまで確認するのかを先に決めることだ。

特に、人名、住所、施設名、CSV、Excel出力のように日本語が多く含まれる機能では、代表データだけでなく、旧字、長い文字列、記号、改行、外部システム由来の文字を含むデータを早めに用意して確認したい。

日本語の文字化けは、海外の記事を検索しても同じ事例が見つかりにくい場合がある。だからこそ、日本語環境で起こりやすい問題として、早めに検証項目へ入れておきたい。

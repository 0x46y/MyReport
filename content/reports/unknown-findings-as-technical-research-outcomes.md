結論から言うと、技術調査では「分からなかったこと」も成果になる。

APIで必要な情報を取得できなかった。ライセンス上の扱いが確認できなかった。ベンダーに問い合わせても対象外だった。データが足りず、PoC（ポック・小規模検証）では判断できなかった。

これらは、単に「失敗した」ではない。次に同じ調査をする人が、同じ場所で時間を使わないための判断材料になる。

この記事では、技術調査で分からなかったことを、どう成果として残すかを整理する。

PoC、API、ライセンス、責任分界点などの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 分からなかったことは失敗とは限らない

技術調査では、分かったことだけが成果に見えやすい。

たとえば、次のような結果は説明しやすい。

- サンプルコードが動いた
- APIからデータを取得できた
- 小規模データで処理できた
- 月額費用の概算を出せた
- 管理画面の試作品を作れた

一方で、次のような結果は成果として見えにくい。

- APIでは必要な項目を取得できなかった
- SDKの説明と実際の挙動が違っていた
- ライセンス上、その使い方が許されるか判断できなかった
- ベンダーサポートの回答範囲では解決しなかった
- 本番相当のデータがなく、精度や性能を判断できなかった
- 社内で誰が承認するのか分からなかった

しかし、実務ではこちらの方が重要になることも多い。

「何が分からなかったか」が残っていないと、後から別の人が同じ調査を繰り返す。過去に試した案が、なぜ止まったのかも分からなくなる。

分からなかったことを残す目的は、責任逃れではない。次の判断を速くするためである。

## 「分からない」にも種類がある

技術調査で出てくる「分からない」は、すべて同じではない。

たとえば、次のように分けられる。

| 区分 | 意味 | 次に必要なこと |
| --- | --- | --- |
| 未調査 | まだ確認していない | 調査対象に入れる |
| 未確認 | 調べたが、確証を持てる材料がない | 追加検証や問い合わせを行う |
| 確認不能 | 公開情報や手元環境では判断できない | ベンダー、契約、社内担当へ確認する |
| 非対応 | 仕様やAPI上、その機能が用意されていない | 別案、範囲縮小、手動運用を検討する |
| 条件付き | ある条件なら成立するが、条件が崩れると使いにくい | 成立条件を明記する |

この区分をしないまま「分かりません」と書くと、調査不足に見えやすい。

しかし、

```text
公開ドキュメント、SDK、サンプルコードを確認したが、
必要な項目を取得するAPIは見つからなかった。
ベンダーへの確認が必要。
```

のように書けば、次に何をすべきかが見える。

## APIやSDKで取得できないことが分かる

外部サービスや業務ソフトを使うとき、画面上では見えている情報でも、APIやSDKから取得できるとは限らない。

たとえば、画面では確認できる項目があっても、APIにはその項目が用意されていないことがある。SDKでは一部の操作だけ対応していて、細かい設定や内部情報には触れないこともある。

この場合、重要なのは「使えなかった」で終わらせないことだ。

確認したいこと:

- 画面上で見える情報とAPIで取れる情報は同じか
- SDKでできる操作と、手動操作でできる操作は同じか
- 非公開APIや内部ファイルに依存していないか
- バージョンやライセンスによって取得できる情報が変わらないか
- ベンダーサポートへ確認する必要があるか

高額な業務ソフトやCAD（キャド・設計支援ソフト）では、この差が大きくなることがある。

この点は [高額な業務ソフトを自動化するときに確認したいこと](/reports/expensive-business-software-automation-checkpoints) とも関係する。

## ベンダーサポートで解決しないこともある

サポート契約があると、困ったときに解決できるように見える。

もちろん、製品の使い方、不具合、設定方法を確認できることは大きな価値がある。

ただし、サポートは万能ではない。

たとえば、次のような場合は、サポートの範囲外になることがある。

- 製品が想定していない使い方をしたい
- 独自の自動化や外部連携をしたい
- 他社製品やOSS（オープンソースソフトウェア）と組み合わせたい
- 社内固有の業務ルールに合わせたい
- 製品の内部構造や非公開仕様に依存したい

このとき、「ベンダーが悪い」と書く必要はない。

むしろ、次のように残した方が判断材料になる。

| 項目 | 内容 |
| --- | --- |
| 確認したこと | 対象製品のAPIで特定データを取得できるか |
| ベンダー回答 | 現行APIでは対象外。標準機能としては未対応 |
| 影響 | 自動化するには別方式、手動確認、範囲縮小が必要 |
| 次の選択肢 | 要望提出、別製品検討、中間形式への変換、手動工程を残す |

この記録があれば、後から「なぜ標準機能でやらなかったのか」を説明しやすくなる。

## ライセンスや契約は技術調査だけでは判断できない

技術的には動くが、ライセンス上その使い方をしてよいか分からないことがある。

たとえば、

- 商用利用してよいか
- 自動処理で大量に使ってよいか
- 変換したデータを別ツールで使ってよいか
- 社外へ配布してよいか
- 外部APIへデータを送ってよいか
- 下請けや別会社の担当者が使ってよいか

といった点は、コードを書いただけでは判断できない。

ここで技術者が無理に断定すると危ない。

技術調査としては、

```text
技術的には実行可能。
ただし、ライセンス上その使い方が許可されるかは未確認。
契約担当またはベンダーへの確認が必要。
```

と残す方がよい。

「分からなかった」と書くことは、調査不足ではなく、判断権限の境界を明確にすることでもある。

## データが足りないと判断できないことがある

AI、検索、分類、最適化、3D処理、文字コード、CSV取込のような調査では、サンプルデータでは問題が見えないことがある。

たとえば、小さな検証では成功しても、次のような条件で問題が出る。

- 本番データ量が多い
- 例外的な文字や旧字が含まれる
- 入力形式が部署や担当者によって違う
- 正解データが少ない
- 用途ごとにデータ構造が違う
- 実際の運用では更新や削除が発生する

この場合、

```text
小規模データでは処理できた。
ただし、本番相当の件数、例外文字、外部システム由来データでは未確認。
現時点では本番導入判断には不足している。
```

と残すことが重要になる。

これは「できない」と言っているのではない。

判断に必要なデータがまだ足りない、という成果である。

この点は [日本語データを扱うシステム開発で確認したいこと](/reports/japanese-text-encoding-system-development) や [AIに専門業務を教える前に確認したい学習データの問題](/reports/ai-training-data-for-specialized-work) ともつながる。

## PoCで判断できることと判断できないことを分ける

PoCは、技術が成立しそうかを小さく確認するために有効だ。

ただし、PoCで分かることと、PoCだけでは分からないことがある。

| PoCで分かりやすいこと | PoCだけでは分かりにくいこと |
| --- | --- |
| 小規模データで動くか | 本番データ量で安定するか |
| 主要APIを呼べるか | 障害時に復旧できるか |
| 画面の操作感 | 現場が継続して使えるか |
| 変換処理の方向性 | 例外データや失敗時の扱い |
| AIの初期精度 | 誤判定時の責任範囲 |
| 初期費用の感覚 | 継続費用や運用人件費 |

PoCの結果を報告するときは、「成功したこと」だけでなく「まだ判断できないこと」も残したい。

たとえば、

```text
PoCでは、主要処理が成立することを確認した。
ただし、運用担当、権限管理、障害時対応、本番データ量での性能は未確認。
本番導入判断には追加確認が必要。
```

のように書く。

この書き方なら、PoCの成果を否定せずに、次の判断条件を明確にできる。

この点は [小さな検証（PoC）が成功しても本番導入できない理由](/reports/poc-success-production-adoption-risks) とも関係する。

## 分からなかったことを報告に残す形

分からなかったことを成果として残すには、ただ「不明」と書くだけでは足りない。

少なくとも、次の形にすると使いやすい。

| 項目 | 書くこと |
| --- | --- |
| 調査したこと | 何を確認しようとしたか |
| 試した方法 | ドキュメント、API、SDK、PoC、問い合わせなど |
| 分かったこと | 確認できた事実 |
| 分からなかったこと | 判断できなかった点 |
| 分からなかった理由 | 情報不足、権限不足、データ不足、契約確認待ちなど |
| 影響 | 採用判断、費用、運用、責任範囲にどう影響するか |
| 次に必要なこと | 追加検証、問い合わせ、別案検討、範囲縮小など |

たとえば、次のように書ける。

| 項目 | 内容 |
| --- | --- |
| 調査したこと | 外部APIで施設情報を自動取得できるか |
| 試した方法 | 公式ドキュメント、APIレスポンス、サンプルコードを確認 |
| 分かったこと | 基本情報は取得できる |
| 分からなかったこと | 更新日時と一部の内部項目は取得できるか不明 |
| 分からなかった理由 | 公開ドキュメントに項目説明がなく、レスポンスにも含まれない |
| 影響 | 差分更新を自動化するには判断材料が足りない |
| 次に必要なこと | ベンダーへ確認。無理なら全件再取得か手動更新を検討 |

ここまで書くと、未解決事項は単なる空欄ではなく、次の行動につながる。

## 「できません」ではなく「この条件では判断できません」と書く

技術調査の報告では、言い方も重要になる。

「できませんでした」だけだと、調査が失敗したように見えやすい。

実際には、条件が足りないだけのこともある。

たとえば、次のように言い換えられる。

| 避けたい書き方 | 判断材料になる書き方 |
| --- | --- |
| できませんでした | 現行APIでは必要な項目を取得できませんでした |
| 分かりません | 公開情報では判断できず、ベンダー確認が必要です |
| 動きません | Edge Runtimeでは動かず、Node.js Runtimeでは追加確認が必要です |
| 精度が出ません | 現在の50件では評価に不足しており、正解データの追加が必要です |
| 無理そうです | 現在のライセンス条件では判断できず、契約確認が必要です |

強く言い切るべき場面もある。

しかし、調査段階では「どの条件では確認できたのか」「どの条件では判断できないのか」を分けた方が、関係者が次の行動を取りやすい。

## 調べ続けるか、いったん止めるかを決める

技術調査では、調べ続ければ必ず答えが見つかるとは限らない。

一定時間調べても、公開情報がない、ベンダー確認が必要、契約上の判断が必要、本番データが存在しない、といった理由で止まることがある。

このときに、何となく調査を続けると時間だけが増えやすい。

たとえば、次のような状態になったら、いったん「現時点では判断できない」と整理することも成果になる。

- 公式ドキュメントとSDKを確認しても必要な情報が見つからない
- ベンダー回答待ちで、社内だけでは判断できない
- ライセンスや契約の確認が必要で、技術者だけでは結論を出せない
- 本番相当のデータや正解データがなく、精度や性能を評価できない
- 追加調査にかかる時間や費用が、今の検証目的に対して大きすぎる

この場合は、次のように書くとよい。

```text
現時点の公開情報と手元環境では判断できない。
追加で判断するには、ベンダー確認、契約確認、本番相当データの提供が必要。
これらが用意できるまでは、本案は保留とする。
```

これは調査を投げ出すことではない。

次の判断に必要な条件を明確にしたうえで、調査をいったん止めるという判断である。

この考え方は [技術調査で撤退条件を決める意味](/reports/technical-research-exit-criteria) ともつながる。

## 成果として残すと次の調査が速くなる

分からなかったことを残しておくと、次の調査が速くなる。

たとえば、半年後に別の担当者が同じ技術を調べることがある。

そのときに、

- どのドキュメントを見たか
- どのサンプルコードを試したか
- どの環境では動かなかったか
- どの問い合わせは回答済みか
- どの条件が未確認か
- なぜその案を保留したか

が残っていれば、同じ調査を繰り返さずに済む。

技術調査は、今の判断のためだけに行うものではない。

次に同じ問題に向き合う人のために、調査コストを減らす記録でもある。

## 報告文に落とすときの形

会社やチームに報告する場合は、次のように書くと伝わりやすい。

```text
【調査テーマ】
対象業務ソフトのAPIで必要データを取得できるか

【確認したこと】
・公式ドキュメントのAPI項目を確認
・サンプルコードでレスポンスを確認
・対象データを取得できるか検証

【分かったこと】
・基本情報はAPIから取得できる
・一部の項目は画面上では見えるが、APIレスポンスには含まれない

【分からなかったこと】
・上位ライセンスで取得できるか
・ベンダー側でAPI追加予定があるか
・内部ファイルを直接読む方法がライセンス上許されるか

【判断】
現時点では、APIだけで完全自動化する判断はできない。
部分自動化、手動確認、別形式への変換を含めて検討する。

【次に確認すること】
・ベンダーへAPI対応状況を確認
・代替形式で取得できる情報を確認
・手動確認を残した場合の作業時間を見積もる
```

この形なら、「分からなかったこと」が失敗ではなく、次の判断材料として伝わりやすい。

## まとめ

技術調査では、「分かったこと」だけでなく「分からなかったこと」も成果になる。

APIで取れない、ライセンス上判断できない、ベンダーサポートでは解決しない、データが足りない、PoCだけでは本番判断できない。これらは、次に確認すべき条件を明らかにする成果である。

大事なのは、「不明」で終わらせないことだ。

何を試したのか。どこまで確認できたのか。なぜ判断できなかったのか。次に誰が何を確認すべきなのか。

そこまで残しておくと、技術調査は単なる作業記録ではなく、次の意思決定に使える資産になる。

結論から言うと、Excelやスプレッドシートは古いから残っているのではなく、現場の人が自分で直せる道具だから残っている。

エンジニアから見ると、Excel管理は壊れやすく、属人化しやすく、データ品質を保ちにくい。しかし、利用者側から見ると、すぐ編集できる、共有しやすい、手元で確認できる、エンジニアへ毎回依頼しなくて済むという強い価値がある。

この記事では、Excelやスプレッドシートを否定するのではなく、どこまでなら表で十分か、どこからDBや管理画面を検討した方がよいかを整理する。

ここで大事なのは、Excelやスプレッドシートを「DB化する前の仮置き」とだけ見ないことだ。条件によっては、表形式の運用自体が現場にとって十分な完成形になることもある。

CSV、DB、CRUD、管理画面、CMSなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## Excelやスプレッドシートには強い理由がある

ExcelやGoogleスプレッドシートは、多くの現場で使われ続けている。

理由は単純で、非エンジニアでも扱えるからだ。

たとえば、次のような強みがある。

| 観点 | 強み |
| --- | --- |
| 編集しやすさ | 画面を見ながらその場で修正できる |
| 導入の速さ | 新しいシステムを作らずに始められる |
| 共有 | ファイル共有やリンク共有で回しやすい |
| 一覧性 | データを表として見渡せる |
| 柔軟性 | 列やメモをすぐ追加できる |
| 自律性 | エンジニアへ依頼せず、自分たちで直せる |

この「自分たちで直せる」はかなり大きい。

現場担当者は、必ずしも高度なシステムを求めているわけではない。むしろ、細かい修正のたびに開発者へ依頼しなくて済むことを重視する場合がある。

これは開発者を避けたいという意味ではなく、都度依頼する手間や気遣いを減らしたいという面もある。

## 小さく始めるなら表で十分なことがある

すべての業務データを最初からDB化する必要はない。

たとえば、次のような条件なら、Excelやスプレッドシートで十分なことがある。

- データ件数が少ない
- 更新者が少ない
- 更新頻度が低い
- 外部公開しない
- 多少の手作業修正を許容できる
- 誤りがあってもすぐ直せる
- まず運用を試したい段階

この段階でいきなりDB、認証、管理画面、権限管理、監査ログまで作ると、初期費用や開発期間が大きくなりやすい。

表で運用してみることで、どの項目が本当に必要か、誰が更新するのか、どの入力ミスが起きやすいのかを先に確認できる。

これは [試作品は完成品ではなく判断材料になる](/reports/prototype-communicates-better-than-proposal) という考え方にも近い。

一方で、小さく始めた表が、そのまま長く使われることもある。

たとえば、更新者が限られていて、データ件数も多すぎず、外部公開や厳密な履歴管理が不要な場合は、Excelやスプレッドシートのまま数年単位で業務が回ることもある。技術的にはDB化できたとしても、利用者にとっては表の方が早く、分かりやすく、引き継ぎやすい場合がある。

つまり、Excelは常に「いつか置き換えるべき暫定運用」ではない。業務の規模やリスクによっては、表形式がちょうどよい落としどころになる。

## Excelはデータベースではなく自由に作れる紙に近い

Excelやスプレッドシートが強い理由は、単に表を作れるからだけではない。

セル結合、色付け、コメント、太字、図形、画像貼り付け、説明文、空行などを使って、人間が読みやすい資料を自由に作れることも大きい。

エンジニアは、次のような整った表を期待しがちだ。

| ID | 施設名 | 住所 |
| --- | --- | --- |
| 1 | A施設 | 東京都... |
| 2 | B施設 | 千葉県... |

しかし現場の資料では、次のような構成になることもある。

- エリア名の見出し行が入る
- 注意事項が途中に入る
- 重要な施設だけ色が付く
- セルが結合されている
- 備考やメモが自由に書かれている
- 空行で区切られている

これはプログラムから見ると扱いにくい。しかし人間から見ると、分かりやすくするための工夫でもある。

ここに、Excelの強さと難しさがある。

Excelには、データベースとして使われるExcelと、人間向けの資料として使われるExcelが混ざりやすい。人間向けの資料としては便利でも、そのままCSV取込や自動処理に使うと、空行、結合セル、途中の説明行、列構成の変更が原因で処理が壊れやすくなる。

つまり、Excelの自由度は、そのままデータ品質や自動化の難しさにもつながる。

## 表管理が苦しくなる条件

一方で、Excelやスプレッドシートは万能ではない。

次のような条件が増えると、表管理は苦しくなりやすい。

| 条件 | 起こりやすい問題 |
| --- | --- |
| 更新者が増える | 誰が何を変えたか追いにくくなる |
| データ件数が増える | 重複、検索、集計、確認が重くなる |
| 外部公開する | 入力ミスが利用者に見える |
| 権限が必要 | 見てよい人、編集してよい人を分けにくい |
| 履歴が必要 | 変更前の状態や変更理由を追いにくい |
| 承認が必要 | 公開前チェックの流れを作りにくい |
| 別システムと連携する | 列名、形式、文字コードの揺れが問題になる |
| 障害時に困る | 誰が復旧するか、どの状態へ戻すかが曖昧になる |

表は柔軟だから便利だ。

しかし、その柔軟さによって、列の意味が変わる、空行が入る、必須項目が空欄になる、想定外の文字が入る、削除してはいけない行が消える、といった問題も起きやすい。

特に、人間向けの資料として作られたExcelを、後からシステム連携用のデータとして扱おうとすると問題が出やすい。見出し行、説明行、セル結合、色分け、備考欄は、人間には意味があっても、プログラムには判断しにくいことがある。

この点は [静的サイトをCMS化する前に確認したいこと](/reports/static-site-before-cms-migration) でも整理している。

## 管理画面は表を置き換えるためだけのものではない

管理画面は、単に「ExcelをWeb化したもの」ではない。

管理画面の価値は、自由に編集できることよりも、安全に編集できることにある。

たとえば、管理画面では次のような制御を入れられる。

- 必須項目を空欄にできない
- 日付や数値の形式を制限する
- 選択肢をプルダウンにする
- 削除前に確認する
- 削除ではなく非表示にする
- 変更履歴を残す
- 管理者だけが編集できるようにする
- 公開前に確認状態を持たせる

これは見た目を整えるためだけではない。

入力ミスや運用ミスを減らし、外部利用者に壊れたデータを見せないための仕組みでもある。

## DB化する前に確認したいこと

ExcelやスプレッドシートからDBへ移す前に、次の点を確認したい。

| 観点 | 確認したいこと |
| --- | --- |
| データ件数 | 今後どれくらい増えるか |
| 更新者 | 誰が登録、編集、削除するか |
| 権限 | 誰が見てよく、誰が編集してよいか |
| 履歴 | 変更履歴や復元が必要か |
| 公開範囲 | 内部利用か、外部公開か |
| 入力制御 | 必須項目、形式、選択肢を制限する必要があるか |
| 連携 | 他システム、CSV、APIとつなぐか |
| 費用 | DB、認証、管理画面、保守の費用を許容できるか |

DB化すると、データ構造を安定させやすくなる。

一方で、設計、移行、バックアップ、権限管理、保守が必要になる。

だから、DB化は「Excelが古いから置き換える」ではなく、「表管理では守れない要件が出てきたから検討する」と考えたい。

## AI時代でも表の強みは残る

AIでコードを書けるようになると、CRUD画面や管理画面は以前より作りやすくなる。

しかし、それでもExcelやスプレッドシートの価値がすぐ消えるわけではない。

なぜなら、表は現場の人にとって、

- データの中身を直接見られる
- すぐ編集できる
- すぐ共有できる
- 計算や並び替えを自分で試せる
- システム化する前の試作品として使える

からだ。

AIがコードを作れることと、現場が安心して運用できることは別だ。

むしろAI時代には、表で見えている現場の運用をどうDBや管理画面へ移すか、その設計が重要になる。

たとえば、AIに「このExcelを読み取って管理画面を作って」と依頼しても、そのExcelがデータベースとしての表なのか、人間向けの報告資料なのかを先に見分ける必要がある。注意書き、色、結合セル、並び順、余白に業務上の意味が含まれている場合、それを単純に削ると現場で使いにくいシステムになる。

この点は [AIでコードを書ける時代に設計が重要になる理由](/reports/ai-code-generation-design-importance) とも関係する。

## 表で続けるか、管理画面を作るか

判断するときは、次のように分けると考えやすい。

| 状況 | 向いている選択 |
| --- | --- |
| 少人数でたまに更新する | Excelやスプレッドシートで十分なことがある |
| 入力形式を守りたい | プルダウン、入力制限、テンプレートを使う |
| 外部公開する | 管理画面や公開前チェックを検討する |
| 更新者が増える | 権限管理や履歴管理を検討する |
| データが増える | DB化や検索機能を検討する |
| 障害時に困る | バックアップ、復旧手順、手動運用を決める |

重要なのは、Excelを使うかDBを使うかを最初から決め打ちしないことだ。

運用の規模、更新者、公開範囲、ミスしたときの影響を見て決めたい。

## まとめ

Excelやスプレッドシートは、古いから残っているのではない。

非エンジニアが自分で見て、直して、共有できるから残っている。

一方で、データ件数、更新者、権限、履歴、外部公開、連携が増えると、表の柔軟さがリスクになることもある。

その場合は、DB、管理画面、CMS、入力制御、権限管理を検討する。

大事なのは、Excelを否定することではない。

表で十分な範囲と、管理画面やDBが必要になる範囲を分けることだ。

業務システムの設計では、現場が自分で直せる自由度と、壊れにくく安全に運用できる制約の両方を考えたい。

そのためには、Excelを「古い道具」として見るのではなく、「人間が自由に業務を表現できる道具」として見る必要がある。その自由度をどこまで残し、どこからシステム側で制約するかが、管理画面やDB化を考えるときの判断材料になる。

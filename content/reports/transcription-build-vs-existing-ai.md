## 結論

文字起こし機能を作り始める前に、録音済みの音声を既存のAIサービスへ渡す方法で目的を満たせないか確認したい。

現在のAIサービスには、音声を文字へ変換するだけでなく、フィラーの整理、誤字の修正、文章の区切り直し、要約まで行えるものがある。必要なのが読みやすい会議記録であれば、専用の文字起こし機能を内製するより、既存の録音手段とAIを組み合わせる方が短期間で実現できる場合がある。

一方、音声を外部へ送信できない、大量の音声を自動処理したい、社内システムと連携したい、といった条件がある場合は、ローカル処理や専用機能の内製が候補になる。

大切なのは、最初から「作る」と決めるのではなく、必要な処理と制約を分けて比較することである。

## 文字起こしは一つの処理ではない

録音した会話から読みやすい記録を作るまでには、少なくとも次の工程がある。

1. 音声を録音する
2. 音声を文字へ変換する
3. 認識結果の誤りを確認する
4. フィラーや重複表現を整理する
5. 読みやすい文に整える
6. 必要に応じて要約や議事録を作る

フィラーとは、「あの」「ええと」「まあ」のように、会話の間を埋める言葉である。発言を正確に記録する用途では残した方がよい場合もあるが、内容を読み返すための記録では整理した方が読みやすい。

これらの工程を一つの専用アプリにまとめることはできる。ただし、すべてを内製すると、録音方式、音声認識モデル、文章補正、保存、画面、配布まで管理対象が広がる。

まず必要な成果物を決めてから、どこまでを既存機能へ任せるか考えたい。

## 先に成果物を決める

「文字起こしがほしい」という依頼でも、必要な結果は用途によって異なる。

| 用途 | 必要になりやすい成果物 |
| --- | --- |
| 発言内容を正確に確認する | 音声に近い未修正版の文字起こし |
| 会議内容を読み返す | フィラーや重複を整理した文章 |
| 決定事項を共有する | 要点、決定事項、担当、期限 |
| 問い合わせ対応を記録する | 時刻、話者、対応内容 |
| 後から検索する | 日付、参加者、分類、全文検索用データ |

必要なのが簡単な要約だけなら、高度な話者分離や秒単位の時刻情報は不要かもしれない。反対に、発言の確認が必要な用途では、AIが読みやすく書き換えた文章だけを残すと、元の発言を確認できなくなる。

機能一覧より先に、何を正しい成果物とするかを決める必要がある。

## 既存AIを使う場合

最も簡単な構成は、既存の録音機能で音声ファイルを作り、そのファイルを音声対応のAIサービスへ渡す方法である。

この方法では、AIへ次のような処理を依頼できる。

- 音声をそのまま文字へ変換する
- 文の区切りと句読点を整える
- フィラーや言い直しを整理する
- 明らかな誤字を修正する
- 要点、決定事項、確認事項を抽出する
- 指定した形式で議事録を作る

録音と文章作成を既存のサービスへ任せられれば、モデルの配布、GPU対応、推論処理の実装を減らせる。少人数で試す場合や、まず業務上の効果を確認したい場合には有力な方法になる。

ただし、AIが文章を読みやすく整える過程で、発言の表現が変わることがある。音声にない説明が追加されたり、数字や固有名詞が誤って補正されたりする可能性もある。

正確さが必要な用途では、人による確認をなくすのではなく、確認しやすい形を作ることが重要である。

## ローカル文字起こしを使う場合

音声を外部へ送信できない場合は、Whisperなどの音声認識モデルをPCや社内環境で動かす方法が候補になる。

ローカル処理の主な利点は、音声データを手元の環境内で処理しやすいことである。一方で、利用するモデルと端末によって、処理速度、認識結果、必要なメモリや保存容量が変わる。

確認したいことは次のとおりである。

- CPUだけで必要な時間内に処理できるか
- GPUが必要なら、利用者の端末に搭載されているか
- モデルを各端末へ配布・更新できるか
- 長時間音声を分割して処理できるか
- 日本語、専門用語、数字、固有名詞をどこまで認識できるか
- 認識後の文章補正をどのように行うか
- 音声と文字起こし結果をどこへ保存するか

ローカル処理で文字へ変換できても、読みやすい文章になるとは限らない。フィラー整理や要約が必要なら、別の文章処理を追加するか、人が編集する必要がある。

## 録音方式にも制約がある

文字起こし精度だけでなく、音声をどのように取得するかも確認したい。

### ブラウザで録音する

ブラウザからマイクやPCの再生音を取得する方法は、専用ドライバーを用意せずに導入しやすい。

一方、画面やシステム音声を取得する場合、利用者による共有対象の選択と許可が必要になる。これはWebページによる無断録音を防ぐための安全上の制約である。ブラウザ側の確認画面を完全に省略できるとは限らない。

### Windowsで直接録音する

Windowsでは、WASAPI（ワサピ・Windowsの音声処理機能）のループバック録音を使い、スピーカーやヘッドホンへ送られる音を取得できる。

ブラウザの共有操作を省ける可能性がある一方、マイクとPC音声を同時に扱う場合は、次の調整が必要になる。

- 使用するマイクと再生デバイスの選択
- 音量のバランス
- 音声形式とサンプルレートの変換
- 二つの音声を開始する時刻の差
- 長時間録音で発生するずれ
- 会議アプリと同時に使用できるか

「録音開始ボタンを一つ置く」という画面上の要望でも、端末や音声デバイスの違いを吸収する実装と検証が必要になる。

## 自作と既存AIを比較する

| 観点 | 専用機能を内製する | 既存の録音手段とAIを使う |
| --- | --- | --- |
| 導入までの時間 | 実装と検証が必要 | 小規模に試しやすい |
| 録音 | 端末ごとの対応が必要 | 既存機能を利用できる |
| 文字起こし | モデルや処理方式を管理する | サービス側へ任せられる |
| 文章の整理 | 補正処理を追加する | 一連の依頼として行いやすい |
| 精度改善 | モデル更新と再評価が必要 | サービス側の改善を利用しやすい |
| 独自連携 | 詳細に作り込める | 提供機能やAPIに依存する |
| 情報管理 | ローカル構成を選べる | 外部送信と契約の確認が必要 |
| 保守 | ライブラリやモデルを管理する | 自作部分を減らせる |
| 費用 | 開発費と保守費が中心 | 利用料や従量課金が中心 |

「無料のローカルモデル」と「有料のAIサービス」だけを比べると、判断を誤りやすい。ローカル処理にも、端末、構築、配布、更新、問い合わせ対応の費用がかかる。

既存AIにも、利用料金、上限、サービス変更、外部依存という制約がある。初期費用だけでなく、継続して利用する場合の費用と担当者まで含めて比較したい。

## 既存AIが向いている条件

次の条件では、まず既存AIを使った小規模な確認が向いている。

- 音声ファイルを外部サービスへ送信できる
- 少人数または少量の音声から始める
- 人が最終結果を確認できる
- 独自画面や複雑なシステム連携が不要である
- 短期間で業務上の効果を確認したい
- 文字起こしだけでなく要約や文章整理も必要である

この場合、最初から専用アプリを作らず、録音方法、AIへの指示、確認手順を先に整える方がよい可能性がある。

## 内製を検討する条件

次の条件がある場合は、専用機能やローカル処理を検討する理由になる。

- 音声を外部へ送信できない
- 大量の音声を定期的に自動処理する
- 社内システムへ自動登録する必要がある
- 話者、承認、保存期限を独自に管理する
- 用語辞書や補正ルールを統一して適用する
- 利用サービスの容量上限や継続費用が合わない
- 元音声から修正版までの処理記録が必要である
- インターネットへ接続できない環境で使用する

この場合も、すべてを自作する必要はない。録音は既存機能、文字起こしは外部または社内API、確認画面だけを内製するなど、必要な部分だけを組み合わせられる。

## 情報管理で確認すること

既存AIを業務で使用する場合は、機能や精度だけで決めない。

- 会議音声を外部へ送信してよいか
- 個人情報、顧客情報、機密情報を含む場合の扱い
- 入力データと生成結果の保存条件
- AIの学習に使用されるか
- 利用者個人の契約ではなく、組織管理の契約が必要か
- 利用量と費用上限を誰が管理するか
- 誤認識を誰が確認するか
- 元音声をいつ削除するか

利用するサービスや契約によって条件は変わる。サービス名だけで安全性を判断せず、実際に利用する機能、契約、設定を確認する必要がある。

## 元の記録と修正版を分ける

文字起こしと文章補正を一度に行うと、どこまでが実際の発言で、どこからがAIによる編集か分かりにくくなる。

正確さが必要な用途では、次の三つを分けて扱いたい。

1. 元の音声
2. 修正前の文字起こし
3. フィラーや誤字を整えた読みやすい版

議事録を作る場合は、さらに要約や決定事項を別の成果物として扱う。最終版だけを残すのではなく、必要に応じて元の発言へ戻れるようにする。

また、保存期間を長くすればよいとは限らない。元音声に機密情報や個人情報が含まれる場合は、確認が終わった後に削除するルールも必要になる。

## 小さく比較する方法

採用前には、利用許可を得た短い音声を使い、候補を同じ条件で比較する。

確認項目は次のように整理できる。

- 発話が欠落していないか
- 音声にない内容が追加されていないか
- 数字、固有名詞、専門用語が正しいか
- 文の区切りが読みやすいか
- フィラー整理後も発言の意味が変わっていないか
- 処理時間は業務上許容できるか
- 人による修正に何分かかるか
- 一回または一時間当たりの費用はいくらか
- 音声を安全に保存・削除できるか

文字数の多さや処理速度だけでは、文字起こしの正確さを評価できない。可能であれば、音声を聞きながら正解文を作り、誤認識と欠落を確認する。

## まとめ

文字起こし機能は技術的に内製できる。しかし、作れることと、作る必要があることは別である。

必要なのが録音後の文字起こし、フィラー整理、誤字修正、要約であれば、既存の録音機能とAIサービスを組み合わせるだけで目的を満たせる可能性がある。

まず次の順序で確認したい。

1. 必要な成果物を決める
2. 既存の録音手段を確認する
3. 音声を外部へ送信できるか確認する
4. 既存AIで小さく比較する
5. 人による確認方法を決める
6. それでも残る独自要件を整理する
7. 独自要件に対して内製費と保守費が見合うか判断する

専用機能の開発は、既存手段では満たせない条件が見えてからでも遅くない。

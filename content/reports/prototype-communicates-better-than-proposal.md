結論から言うと、システム開発の試作品は、完成品の代わりではなく、認識合わせと判断のための材料として使うと価値が出やすい。

試作品があると、何を作るのか、何を後回しにするのか、どれくらいの期間や費用がかかりそうかを具体的に相談しやすくなる。

文章や図は重要だが、読む人によって想像する画面、操作、データ、運用手順が変わりやすい。一方で、実際にクリックできる画面や、データを登録・検索・編集できる試作品があると、発注側と開発側の認識差を早く見つけやすい。

この記事では、試作品を作る意味を「完成品の先出し」ではなく、何を作るか、何を後回しにするか、どこに費用がかかるかを相談するための手段として整理する。

PoC、CRUD、管理画面、DB、認証などの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 提案書だけでは想像が分かれやすい

提案書には、目的、背景、機能一覧、画面イメージ、費用、スケジュールを書ける。

ただし、提案書だけでは次のような認識差が残りやすい。

| 観点 | 起こりやすいズレ |
| --- | --- |
| 画面 | 一覧画面、入力画面、検索画面の具体的な操作感が想像と違う |
| データ | どの項目を登録するのか、どこまで必須なのかが曖昧 |
| 権限 | 誰が閲覧、登録、編集、削除できるのかが曖昧 |
| 運用 | 誰がデータを更新するのか、更新頻度がどれくらいか見えにくい |
| 例外 | 入力ミス、重複、空欄、古いデータをどう扱うかが残りやすい |
| 費用 | どの機能が費用や期間を増やすのか伝わりにくい |

発注側が悪いという話ではない。文章を読んだだけで、利用者、管理者、開発者、営業、上司が同じ画面を想像するのは難しい。

だからこそ、早い段階で小さく動くものを見せる価値がある。

## 試作品は完成品ではなく認識合わせの道具

試作品を作る目的は、最初から完成品を作ることではない。

むしろ、次のような問いを早く出すことに価値がある。

- この画面なら現場の人が使えそうか
- 入力項目は多すぎないか
- 検索条件は足りているか
- データの更新担当者は誰か
- 管理画面は必要か
- CSV入出力で足りるか
- ログインや権限管理はどこまで必要か
- スマホで使うのか、PC中心なのか

ここで重要なのは、試作品を見せた結果として「やっぱり違う」と分かることも成果だという点だ。

提案書だけで進めると、認識差が開発後半まで残ることがある。小さな試作品があれば、早い段階で方向修正しやすい。

## PoCと試作品は少し目的が違う

PoCは、技術的に成立するかを確認する小さな検証として使われることが多い。

一方で、ここでいう試作品は、技術だけでなく、利用者や発注者との認識合わせにも使う。

| 種類 | 主な目的 | 確認したいこと |
| --- | --- | --- |
| PoC | 技術的に動くか | API、DB、認証、外部連携、性能、実行環境 |
| 画面試作品 | 使い方が伝わるか | 画面遷移、入力項目、検索、操作感 |
| 業務試作品 | 業務に合うか | 誰が更新するか、例外処理、承認、権限 |
| 提案用デモ | 判断しやすいか | 費用感、開発範囲、優先順位、次の相談内容 |

もちろん、1つの試作品がPoCと画面試作品を兼ねることもある。

ただし、何を確認するための試作品なのかを先に決めないと、「動いたが判断材料にならない」という状態になりやすい。

## CRUDアプリは業務システムの最小単位になりやすい

業務システムの試作品として分かりやすいのは、CRUDアプリだ。

CRUDは、Create、Read、Update、Delete の略で、データを登録、表示、更新、削除する基本操作を指す。

たとえば、次のような管理画面がある。

- 施設を登録する
- 施設一覧を見る
- 施設名や地域で検索する
- 施設情報を編集する
- 古いデータを削除または非表示にする

これは特別に派手な機能ではない。しかし、多くの業務システムは、この基本操作を業務ルールに合わせて組み合わせたものでもある。

ここで間違えやすいのは、ORMとCRUDを混同することだ。

ORMは、PrismaやSQLAlchemyのように、プログラムからDBを扱いやすくするための仕組み。利用者が触るアプリそのものではない。

一方で、CRUDアプリや管理システムは、利用者が画面からデータを登録、検索、編集するためのアプリだ。

つまり、発注者に見せる成果物として分かりやすいのは「ORMを使いました」ではなく、「施設情報を登録・検索・更新できる管理画面があります」という形だ。

## CMS型の管理画面は横展開しやすい

CMS型の管理画面は、単なるブログ管理ではなく、認証、DB、CRUD、権限管理、ファイル管理、公開フローを含む小さな業務システムとして扱える。

記事サイトやナレッジサイトを運用している場合、記事をMarkdownファイルで直接編集する方法もある。

この方法は自由度が高く、Git管理やAIコーディングとも相性がよい。一方で、画像の貼り付け、下書き、公開状態、カテゴリ、タグ、関連記事、ロードマップへの追加を毎回手作業で扱うと、運用が重くなることがある。

そのため、CMS型の管理画面は、管理画面付きアプリの試作品として分かりやすい。

たとえば、次のような機能だ。

- 記事を作成する
- 下書きと公開を切り替える
- カテゴリやタグを設定する
- 関連記事を選ぶ
- ロードマップ上の位置を設定する
- 画像やスクリーンショットを管理する

さらに、同じ仕組みは次のような用途へ横展開しやすい。

- 技術ナレッジベース
- 社内FAQ
- 施設情報サイト
- 事例紹介サイト
- 小規模な業務マニュアル

ただし、CMSは既存サービスも多い。自作する価値が出るのは、独自の表示、独自のワークフロー、AIによる記事整理、複数サイトへの展開、データ構造の自由度が必要な場合だ。

## 業務調整ツールはドメイン知識が価値になる

一方で、より業務寄りの試作品としては、スケジュール調整や担当者割当のようなツールも価値がある。

たとえば、外出を伴う業務、当番、施設対応、担当者割当のような業務では、単なるカレンダーでは足りないことがある。

次のような条件が絡むからだ。

- 特定の曜日に対応できない人がいる
- 資格者や責任者が最低1人必要になる
- 経験が浅い担当者だけでは対応できない
- 遠方対応や高負荷な業務を連続させたくない
- 研修、繁忙期、大きなイベントの直後は負荷を下げたい
- 対応先ごとに必要人数や必要条件が違う
- できるだけ公平に割り当てたい

これは単なる予定表ではなく、制約を満たす組み合わせを探す問題に近い。

AI時代に価値が残りやすいのは、このような業務ルールをどうソフトウェアへ落とすかだと考える。

AIはReactやDB操作のコードを書くことはできる。しかし、どの条件を優先するのか、どの例外を許容するのか、誰の負荷を下げるべきか、どの割当が現場で受け入れられるかは、業務を知る人と一緒に整理する必要がある。

この意味で、業務調整ツールは「技術力を見せる試作品」だけでなく、「業務理解と技術をつなぐ試作品」になる。

## 試作品で確認したいこと

試作品を作るときは、最初に確認したい問いを決めておきたい。

| 観点 | 確認したいこと |
| --- | --- |
| 使い方 | 利用者が迷わず操作できるか |
| データ | 必要な項目、入力形式、更新頻度は合っているか |
| 権限 | 誰が閲覧、登録、編集、削除できるか |
| 運用 | 誰が日常的に更新し、誰が問い合わせを受けるか |
| 費用 | この規模ならどれくらいの期間と費用になりそうか |
| 横展開 | 似た業務へ流用できる部分はどこか |
| 除外範囲 | 最初から作らない機能は何か |

小さな試作品を見せると、「この機能も欲しい」という話が出やすい。

それ自体は悪くない。ただし、出てきた要望をすべて初期開発に入れると、費用や期間が膨らみやすい。

だから、試作品を見せるときは、次のように分けたい。

- 初期版に入れる機能
- 次の段階で検討する機能
- 運用で代替する機能
- 今回は作らない機能

この切り分けができると、試作品は単なるデモではなく、見積もりや開発範囲を決める材料になる。

## 横展開できる部分と業務固有の部分を分ける

小さな試作品があると、利用者が判断しやすくなるだけでなく、開発側も工数や費用を見積もりやすくなる。

たとえば、施設管理、顧客管理、設備管理、在庫管理、問い合わせ管理は、扱う業務は違っても、次のような共通部品を持つことが多い。

- ログイン
- 一覧
- 検索
- 登録
- 編集
- 削除または非表示
- CSV入出力
- 権限管理

この共通部分は、別の業務にも横展開しやすい。一方で、どの項目を必須にするか、誰が承認するか、どの例外を許容するか、どの条件を優先するかは業務ごとに変わる。

そのため、試作品を見せるときは、「どこまでが共通部品で、どこからが業務固有のルールなのか」を分けて考えたい。これが分かると、似た仕組みを別業務へ展開する場合の期間や費用も説明しやすくなる。

## AI時代のエンジニアに残る仕事

AIで画面やコードを作ること自体は以前より簡単になっている。しかし、何を作るべきかを決める仕事は残る。

業務システムでは、コードを書く前に決めることが多い。

- 何を作るか
- 誰が使うか
- どのデータを扱うか
- どの制約を守るか
- どの業務ルールを優先するか
- どこまでを自動化するか
- どこから人間が判断するか
- 失敗時に誰が直すか

AIは実装を助けるが、業務の前提や現場の制約を自動で理解してくれるわけではない。

そのため、これからのエンジニアには、技術だけでなく、業界、業務、データ、運用、ハードウェア、現場の制約を理解し、試作品として形にする力が重要になると考える。

これは「AIに置き換えられない仕事を探す」というより、AIを使って、業務側の人と早く同じものを見ながら相談できる状態を作るという話だ。

## まとめ

提案書は重要だが、提案書だけでは認識差が残りやすい。

小さく動く試作品があると、画面、データ、操作、権限、運用、費用、開発範囲について具体的に話しやすくなる。

特に、CMS型の管理画面や業務調整ツールのような試作品は、DB、認証、CRUD、権限管理、運用フローをまとめて示しやすい。

AI時代には、コードを書くことだけでなく、業務の制約を理解し、試作品として見せ、関係者が判断できる状態にすることがより重要になる。

試作品は、完成品の代わりではない。

発注側と開発側が、同じものを見ながら「何を作るか」「何を後回しにするか」「どこに費用がかかるか」を相談するための判断材料だ。

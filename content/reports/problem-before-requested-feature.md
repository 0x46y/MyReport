結論から言うと、システム開発では「作ってほしいもの」だけでなく、「解決したい問題」を先に伝えた方がよい。

「この画面を作ってほしい」「このボタンを追加してほしい」「ExcelをWeb化してほしい」という依頼は分かりやすい。一方で、その依頼だけだと、本当に解決したい問題が見えにくいことがある。

同じ画面を作るより、入力項目を減らす方がよいかもしれない。管理画面を作るより、スプレッドシート運用を少し整える方がよいかもしれない。AIを入れるより、確認フローを変える方が効果があるかもしれない。

この記事では、システム開発を相談するときに、作りたい機能より先に解決したい問題を共有する理由を整理する。

要件定義、PoC、CRUD、CMSなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 作ってほしいものは解決策の一つでしかない

システム開発の相談では、最初から作るものが決まっているように見えることがある。

たとえば、次のような依頼だ。

- 管理画面を作りたい
- 予約フォームを作りたい
- ExcelをDB化したい
- AIで自動分類したい
- スマートフォンから入力できるようにしたい
- 一覧画面に検索機能を付けたい

これらは重要な要望である。

ただし、これらは「解決策の候補」であって、問題そのものではない。

たとえば、「検索機能を付けたい」という要望の裏には、次のような問題があるかもしれない。

- 件数が増えて探しにくい
- 表示項目が多すぎて見落とす
- 担当者ごとに探し方が違う
- 古いデータと新しいデータが混ざっている
- そもそも必要な情報が登録されていない

この場合、検索機能を付けるだけで解決するとは限らない。

問題によっては、データ項目の整理、表示順の変更、不要データの非表示、入力ルールの見直しの方が効果的なこともある。

## 「この機能がほしい」だけだと選択肢が狭くなる

作ってほしいものだけを伝えると、開発側はその機能をどう作るかに集中しやすい。

もちろん、依頼された機能を正しく作ることは大事だ。

しかし、問題が共有されていないと、別の解決策を提案しにくくなる。

たとえば、次のような違いがある。

| 伝え方 | 開発側が考えやすいこと |
| --- | --- |
| CSV出力ボタンを作ってほしい | どの画面にボタンを置くか、どの形式で出すか |
| 月末集計を手作業で作るのに時間がかかっている | CSV出力、集計画面、定期レポート、自動通知などの選択肢 |
| AIで分類したい | どのAIを使うか、どう実装するか |
| 問い合わせの一次振り分けに時間がかかっている | ルール分類、AI候補提示、人の確認、テンプレート整備などの選択肢 |

「作るもの」ではなく「困っていること」が共有されると、選択肢が増える。

開発側も、技術、費用、運用負荷、実装期間を見ながら代替案を出しやすくなる。

## 解決したい問題を伝えると見積もりもしやすくなる

見積もりを出すときも、作るものだけでは判断しにくい。

たとえば、「管理画面を作りたい」と言われても、次の条件で工数は変わる。

- 誰が使うのか
- 何件くらいのデータを扱うのか
- 下書きや承認が必要か
- 画像やファイルを扱うか
- 権限管理が必要か
- 誤削除時に復旧できる必要があるか
- 外部公開する情報か
- 既存データを移行する必要があるか

一方で、

```text
施設情報の更新を毎回エンジニアへ依頼している。
更新頻度は月数回だが、担当者が自分で直せるようにしたい。
ただし、外部公開する情報なので誤更新は避けたい。
```

のように問題と条件が分かると、判断しやすくなる。

この場合、専用管理画面、スプレッドシート運用、CMS、CSV取込、承認フロー付き管理画面などを比較できる。

何を作るかだけでなく、何を避けたいかまで分かると、費用や期間の見積もりも現実に近づく。

## 業務側が持っている情報は技術者には見えにくい

技術者は、実装方法やシステム構成を考えることはできる。

しかし、業務側が持っている情報までは、最初から分からない。

たとえば、次のような情報だ。

- どの作業に時間がかかっているか
- どの入力ミスが多いか
- 誰が確認しないといけないか
- どの例外がよく起きるか
- どの情報は外部に出してはいけないか
- 繁忙期や締切がいつか
- 現場が新しい操作を覚えられるか

これらは、画面仕様だけを見ても分からない。

そのため、開発側に伝えるときは、完成イメージだけでなく、困っている作業、よく起きる例外、避けたい事故も共有した方がよい。

この点は [技術者が決めることと業務担当者が決めること](/reports/engineer-business-decision-boundary) とも関係する。

## 技術側は問題を聞いてから実装案を出す

一方で、開発側も「言われたものをそのまま作る」だけではなく、問題を確認した方がよい。

たとえば、次のように聞く。

- その機能で何を減らしたいのか
- 今はどうやって作業しているのか
- どの作業が一番時間を使っているのか
- どのミスが一番困るのか
- 誰が使うのか
- どの頻度で使うのか
- どこまで自動化したいのか
- 人の確認を残す必要があるか

この確認をしないまま進めると、機能は完成しても、問題は残ることがある。

たとえば、入力画面を作ったが、入力項目が多すぎて現場が使わない。AI分類を作ったが、誤分類時の確認者が決まっていない。管理画面を作ったが、誰が公開前に確認するか決まっていない。

技術側は、問題を聞くことで、実装方法だけでなく、運用条件や責任範囲も整理しやすくなる。

## 伝えるときの形

システム開発を相談するときは、次のような形で伝えると話が進みやすい。

| 項目 | 伝える内容 |
| --- | --- |
| 困っていること | 何に時間がかかっているか、何がミスになっているか |
| 今のやり方 | Excel、紙、メール、既存システムなど |
| 影響 | どのくらい時間がかかるか、誰が困るか |
| 避けたいこと | 誤公開、誤削除、二重入力、確認漏れなど |
| 使う人 | 現場担当、管理者、外部利用者など |
| 頻度 | 毎日、月1回、繁忙期だけなど |
| 判断が必要なこと | 誰が確認、承認、公開、削除を決めるか |
| できれば欲しいもの | 画面、検索、通知、CSV出力、AI分類など |

この順番にすると、「作ってほしいもの」が最後に来る。

先に問題を共有し、そのうえで解決策の候補として機能を話す方が、無駄な開発を減らしやすい。

## 「この画面を作る」から「この作業を軽くする」へ

依頼の言い方を少し変えるだけで、開発側が考えられる範囲は広がる。

たとえば、次のように言い換えられる。

| 機能中心の言い方 | 問題中心の言い方 |
| --- | --- |
| 検索画面を作ってほしい | 必要な情報を探すのに時間がかかっている |
| CSV出力がほしい | 月末集計を手作業で作っている |
| 管理画面がほしい | エンジニアに依頼しないと情報を更新できない |
| AIで自動分類したい | 問い合わせの振り分けに時間がかかっている |
| スマホ対応してほしい | 外出先で確認できず、戻ってから二重入力している |

機能中心の言い方が悪いわけではない。

ただし、問題中心の言い方があると、開発側は「本当にその機能が必要か」「もっと小さい方法で解決できないか」「本番運用まで考えると別案がよいのではないか」を検討しやすい。

## 試作品は問題を確認するためにも使える

問題を言葉だけで共有するのは難しいことがある。

その場合、小さな試作品を作ると、認識合わせがしやすくなる。

たとえば、簡単な画面、スプレッドシート、プロトタイプ、モック、AIの候補出力を見ながら、

- この入力項目で足りるか
- この一覧で探せるか
- この承認フローで回るか
- このAI結果を人が確認できるか
- この操作なら現場の負担が減るか

を確認できる。

試作品は完成品ではない。

作るべきものを決めるための判断材料である。

この点は [試作品は完成品ではなく判断材料になる](/reports/prototype-communicates-better-than-proposal) ともつながる。

## まとめ

システム開発では、「作ってほしいもの」より先に「解決したい問題」を伝えたい。

画面、ボタン、AI、管理画面、DB化は解決策の候補である。大事なのは、何に困っていて、何を減らしたくて、どのミスを避けたくて、誰が使い、誰が判断するのかを共有することだ。

問題が共有されると、開発側は複数の解決策を比較しやすくなる。発注側も、費用、期間、運用負荷、優先順位を相談しやすくなる。

「この画面を作る」だけでなく、「この作業を軽くする」「この確認漏れを減らす」「この判断をしやすくする」と考えることで、システム開発は実際の業務改善につながりやすくなる。

結論から言うと、Cloudflareは個人開発や小さなWebサービスを素早く公開するにはかなり扱いやすい。一方で、複数システム、複数顧客、複数チームを同じアカウント内で運用する場合は、リソースの分け方、請求の見え方、権限管理を先に考えたい。

GCPのProjectやAzureのResource Groupのような中間レイヤーを前提にしてCloudflareを見ると、Workers、R2、D1、KVなどがアカウント配下に並びやすく、案件単位やサービス単位の整理を自分たちで補う必要が出る。

この記事では、Cloudflareに対する不満ではなく、Cloudflareを複数システムで使う前に確認したいリソース管理の観点を整理する。

Cloudflare Workers、R2、D1、IAM、egressなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## プロジェクト層があると何がうれしいのか

クラウドでいうプロジェクト層は、単なるフォルダではない。

複数のリソースをまとめて、次のような単位を作るために使われる。

| 観点 | プロジェクト層に期待すること |
| --- | --- |
| 所属 | どのサービス、顧客、環境のリソースか分かる |
| 権限 | 誰がどのリソースを操作できるか分ける |
| 請求 | どのプロジェクトがどれくらい費用を使ったか見る |
| 削除 | 不要になったリソースをまとめて消しやすい |
| 監査 | 変更履歴や操作ログをプロジェクト単位で追いやすい |
| 環境分離 | 本番、検証、開発を分けやすい |

個人開発で1つのサイトだけを運用している間は、この差はあまり気にならない。

しかし、サービスが増えたり、顧客ごとに環境を分けたり、チームメンバーを追加したりすると、「どのリソースがどのシステムのものか」を明確にしたくなる。

個人開発でも、複数のWorkersサイト、R2バケット、D1データベースを試していると、最初は問題にならなくても、後から「これはどのサイト用に作ったものだったか」を思い出しにくくなることがある。

## GCPやAWSでは分離単位が先に用意されている

GCPでは、Organization、Folder、Project、Resourceという階層でリソースを整理する。公式ドキュメントでも、ProjectはGoogle Cloudサービスを作成、有効化、課金、権限管理するための基本的な整理単位として説明されている。

AWSでは、アカウントが権限、セキュリティ、コスト、ワークロードの自然な境界になる。AWS Organizationsを使うと、複数アカウントの作成、グルーピング、ポリシー適用、請求の簡素化を行える。

つまり、GCPはProject、AWSはAccountを中心に、リソース、権限、請求を分ける設計が取りやすい。

この考え方に慣れていると、Cloudflareでも同じように「プロジェクトを作って、その中にWorkers、R2、D1を入れる」と考えたくなる。

## CloudflareではAccount配下にリソースを置く感覚が強い

Cloudflareでは、Account、Zone、Workers、R2、D1、KVなどの単位がある。

ドメインに関係する設定はZone単位で扱う。一方で、Workers、R2、D1、KVなどの開発者向けリソースは、Account配下のリソースとして扱う場面が多い。

公式ドキュメントでは、Cloudflare OrganizationsはEnterprise向けの機能として、複数アカウントを管理する上位コンテナと説明されている。これは複数アカウントを束ねる仕組みであり、GCP Projectのように1アカウント内の複数プロジェクトを細かく分ける仕組みとは役割が違う。

そのため、2026年6月時点で自分が確認した範囲では、Cloudflare上で複数システムを運用する場合、GCP Projectのような中間レイヤーを前提にせず、自分たちで命名、アカウント分離、計測、ドキュメント化を考える必要がある。

## どこで困りやすいか

Cloudflareで1つのサイトだけを運用する場合、リソースが少ないので問題になりにくい。

しかし、次のような状況になると、管理の難しさが見えやすい。

- 複数のWebサイトを同じCloudflareアカウントで運用する
- Workers、R2、D1、KVが増えてくる
- 本番、検証、開発を分けたい
- 顧客ごとに利用料金を見たい
- チームメンバーごとに触れる範囲を分けたい
- SaaSでテナントごとの利用量を計測したい
- 不要なリソースを安全に削除したい

このときに困るのは、「動かない」ことではない。

むしろ、動くものは作れるが、後から管理しにくくなることだ。

## 命名規則は最初に決めたい

すぐできる対策は、命名規則を決めることだ。

たとえば、Workers、R2、D1、KVを次のような規則で作る。

```text
{system}-{env}-{resource}
```

例:

```text
myreport-prod-worker
myreport-prod-assets-r2
myreport-prod-main-d1
myreport-dev-worker
client-a-prod-api-worker
client-a-prod-main-d1
```

命名規則だけでは、請求や権限は完全には分離できない。

しかし、ダッシュボード上でリソースを見たときに、どのシステムのものか分かるようになる。

逆に、次のような名前が増えると後から混乱しやすい。

```text
test-worker
main-db
assets
worker-v2
new-api
```

小さな検証なら問題にならないが、本番環境や複数案件では、命名だけで所属と環境が分かるようにしておきたい。

## 請求分離が必要ならアカウント分離も考える

Cloudflareでは、請求は基本的にアカウント単位で見ることになる。

そのため、顧客ごと、事業ごと、サービスごとに費用を厳密に分けたい場合は、最初からアカウントを分ける選択肢もある。

アカウントを分けると、請求や権限は分けやすくなる。

一方で、管理するアカウントが増える。Wranglerの設定、APIトークン、ドメイン、環境変数、デプロイ手順、チームメンバー管理も増える。

つまり、アカウント分離は万能ではない。

| 方法 | 向いているケース | 注意点 |
| --- | --- | --- |
| 1アカウント内で命名規則 | 個人開発、小規模サイト、少数サービス | 請求や権限は完全には分離しにくい |
| アカウント分離 | 顧客ごと、事業ごとに請求や権限を分けたい | 管理対象、デプロイ設定、認証情報が増える |
| 利用量を自前計測 | SaaSやテナント別課金 | 計測ロジックや集計基盤を自分で作る必要がある |

重要なのは、最初に「何を分けたいのか」を決めることだ。

請求を分けたいのか、権限を分けたいのか、ダッシュボード上で見やすくしたいだけなのかで、選ぶ対策は変わる。

## SaaSでは自前のメータリングが必要になることがある

SaaSでテナントごとに従量課金を行う場合、クラウド事業者の請求書だけでそのまま顧客別請求に使えるとは限らない。

Cloudflare Workers、R2、D1、Workers AIなどを使う場合でも、テナントごとにどれだけ使ったかを自分のアプリ側で記録する必要が出ることがある。

たとえば、次のようなデータを自前で残す。

- テナントID
- APIリクエスト数
- 保存容量
- AI推論回数
- トークン数
- ファイルダウンロード量
- 処理時間

このような利用量の記録は、単なるログではない。

将来の料金設計、プラン設計、過剰利用の検知、障害調査にも関係する。

Cloudflare側の分析機能やGraphQL API、Analytics Engineを使える場面もあるが、それを請求根拠として使えるか、どの粒度で集計できるかは別途確認したい。

## 個人開発では気にしすぎなくてもよい

一方で、個人開発や1つの小さなサイトでは、最初から大きなリソース管理を設計しすぎる必要はない。

Cloudflareの強みは、Workers、Static Assets、R2、D1などを低コストで素早く試しやすいところにある。

個人サイトや小さな検証なら、まずは1アカウント内で分かりやすい命名規則を決めるだけでも十分なことが多い。

ただし、次の段階へ進むなら、リソース管理の方針を見直した方がよい。

- サイトやアプリが増えてきた
- 顧客ごとに費用を分けたい
- チームメンバーを追加する
- 本番と検証を明確に分けたい
- SaaSとしてテナントごとに課金したい
- 削除してはいけないリソースが増えてきた

このタイミングで、命名規則、アカウント分離、権限、計測、ドキュメントを見直すとよい。

## 確認したいこと

Cloudflareで複数システムを運用する前に、次の点を確認したい。

| 観点 | 確認したいこと |
| --- | --- |
| 所属 | どのWorkers、R2、D1、KVがどのシステムに属するか |
| 環境 | 本番、検証、開発をどう分けるか |
| 命名 | リソース名だけで所属と環境が分かるか |
| 請求 | 顧客別、サービス別に費用を見る必要があるか |
| 権限 | メンバーごとに触れる範囲を分ける必要があるか |
| 削除 | 不要なリソースを安全に消せるか |
| 計測 | テナント別、顧客別の利用量を自前で記録する必要があるか |
| 移行 | 将来アカウントを分ける可能性があるか |

この確認をせずにリソースを増やすと、最初は速く作れても、後から整理しにくくなる。

## まとめ

Cloudflareは、個人開発や小さなWebサービスを低コストで素早く公開するにはかなり強い。

一方で、複数システム、複数顧客、複数チームを扱う場合は、GCP Projectと同じ役割を持つ中間レイヤーを前提にして設計しない方がよい。

重要なのは、「Cloudflareはだめ」という話ではない。

Cloudflareを使うなら、どの単位でリソース、請求、権限、環境、利用量を分けるのかを先に決めることだ。

個人開発なら命名規則で十分なこともある。顧客別請求やチーム運用が必要なら、アカウント分離や自前計測を検討した方がよい。

クラウド選定では、動かしやすさだけでなく、増えた後にどう管理するかも判断材料にしたい。

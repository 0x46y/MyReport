結論から言うと、AIに専門業務を任せるときに難しいのは、AIに答えを出させることだけではなく、何を正解として教えるかを用意することだ。

AIは大量の一般知識を持っているように見える。しかし、社内固有の設計ルール、業務判断、過去の失敗、現場の暗黙知まで最初から理解しているわけではない。専門業務で使うには、正解データ、データ形式、評価基準、運用上の判断条件を人間側が整理する必要がある。

この記事では、AI導入やファインチューニングを考える前に確認したい、学習データの量、品質、形式、文脈、評価基準の問題を整理する。

PoC、API、ファインチューニング、B-Repなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## AIにとって難しいのは正解を教えること

AIを業務に使うとき、最初に考えがちなのは「AIにできるか」だ。

しかし専門業務では、それ以前に次の問題がある。

- 何を正解とするのか
- 正解データは十分な数があるのか
- その正解は今の業務でも有効なのか
- データ形式はそろっているのか
- 評価基準は人によってぶれないのか
- 失敗したときに誰が確認するのか

たとえば、AIに「よい設計案」を出してほしいとしても、よい設計とは何かを定義できなければ学習も評価も難しい。

強度、コスト、加工しやすさ、メンテナンス性、納期、既存設備との相性、安全率、過去の不具合回避など、複数の条件が絡む場合、単純な正解ラベルを付けにくい。

つまり、AI導入では、モデル選定だけでなく「正解をどう作るか」が大きな仕事になる。

## データが大きいほど、お手本を用意しにくい

学習や検証に使うデータは、種類によって扱いやすさが大きく変わる。

ざっくり言えば、次の順にデータ量や扱う手間は増えやすい。

| データ | 扱いやすさの目安 | 難しくなる理由 |
| --- | --- | --- |
| テキスト | 比較的扱いやすい | 文字列として保存、検索、比較しやすい |
| 画像 | 中程度 | 解像度、ラベル、権利、画質の管理が必要 |
| 音声 | 中程度 | 文字起こし、話者、ノイズ、長さの管理が必要 |
| 動画 | 重い | 時間軸、音声、画像、編集点が絡む |
| 3Dデータ | 重い | 形状、座標、面、エッジ、単位、形式差分が絡む |
| 3D動画やシミュレーション | 非常に重い | 時間変化、物理条件、計算結果、容量が大きい |

テキストは比較的AIに渡しやすい。資料を分割して検索したり、要約したり、分類したりしやすい。

一方で、動画、3D、CAD、シミュレーションのようなデータは、容量が大きく、形式も複雑になりやすい。正解データを集めるだけでなく、AIが扱える形に変換する前処理が大きな負担になる。

この点は [3Dデータ自動化で工数が増えやすい理由](/reports/3d-data-size-cloud-cost-test-explosion) とも関係する。

## 専門業務では正解データの数が足りないことがある

AIに専門業務を教えるには、お手本になるデータが必要になる。

しかし、実務ではここで詰まりやすい。

たとえば、3D設計の正解を出すAIを作りたいとする。

この場合、次のようなデータが必要になる。

- 過去の設計データ
- 条件と設計結果の対応
- なぜその形状にしたのか
- 採用しなかった案
- 不具合が起きた案
- 設計者の判断理由
- 評価結果

しかし、社内に過去データがあっても、そのまま学習に使えるとは限らない。

実際には、次のような問題が起きやすい。

- 数百件から数千件の正解データがそろわない
- 用途や条件がばらばら
- 作成時期が違い、設計ルールが変わっている
- ファイル形式やバージョンが違う
- 判断理由が残っていない
- 成功例はあるが失敗例が残っていない
- 人によって「よい設計」の基準が違う

AIに教えたい対象が専門的であるほど、データの数だけでなく、データの意味をそろえることが難しくなる。

## データ形式がばらばらだと前処理が重くなる

AIに学習させる前には、データをそろえる必要がある。

しかし、業務データは最初からAI向けに整理されているわけではない。

たとえば、次のような状態になりやすい。

| 状態 | 起こりやすい問題 |
| --- | --- |
| 独自バイナリ形式 | 中身を直接読みにくい |
| 古いソフトの形式 | 変換ツールやライセンスが必要になる |
| ExcelやCSV | 列名、文字コード、空行、入力ゆれがある |
| PDFや画像 | 表や注釈を取り出す前処理が必要になる |
| 3D/CADデータ | 形状、単位、座標、属性情報の解釈が必要になる |
| 画面からしか見えない情報 | UI操作やスクレイピングが必要になる |

特に、独自のバイナリ形式や専用ソフト内に閉じたデータは扱いにくい。

人間はアプリの画面を見れば理解できても、AIやプログラムが直接扱うには、エクスポート、変換、スクレイピング、API連携、画面要素の取得などが必要になる。

つまり、AI導入の前に、データを取り出すための技術調査が必要になることがある。

この点は [CATPart、STL、IGES、STEPは何が違うのか](/reports/cad-file-formats-native-stl-iges-step) や [日本語データを扱うシステム開発で確認したいこと](/reports/japanese-text-encoding-system-development) ともつながる。

## LoRAやファインチューニングでも、お手本データは必要

最近は、ゼロからAIを作るのではなく、既存の大規模モデルを使い、追加学習やLoRAで専門領域に寄せる方法がある。

これは、何も知らない状態のAIに一から教えるより、すでに言葉や一般知識を持っているAIに専門知識を追加するイメージに近い。

言い換えると、何も知らない相手に最初から教えるのではなく、すでに一般知識を持っている相手に、自社固有のルールや判断基準を追加で教えるイメージに近い。

そのため、必要なデータ量は少なくできる場合がある。

ただし、それでもお手本データは必要だ。

たとえば、次のような点は人間側で用意する必要がある。

- どの入力に対して、どの出力を正解とするか
- どの失敗例を避けたいか
- どの表現や形式で出力してほしいか
- 社内ルールとして許される判断は何か
- 専門家が見たときに不自然ではないか
- 評価用データを学習用データと分けているか

大規模モデルは一般知識を持っているが、社内固有の前提や専門家だけが知っている違和感まで保証するわけではない。

「AIに聞けば分かる」ではなく、「AIに何を正解として見せるか」を決める必要がある。

## 正解が一つでない業務では評価基準が必要になる

チェスや囲碁のように、ルールと勝敗が明確な領域では、AIは非常に強い。

一方で、業務では正解が一つとは限らない。

たとえば、次のような判断は、単純な正解データにしにくい。

- コストを優先するか、品質を優先するか
- 納期を優先するか、保守性を優先するか
- 既存運用に合わせるか、運用を変えるか
- 短期的な効率を取るか、障害時の余裕を残すか
- 誰の負担を減らし、誰の確認作業を増やすか

このような判断では、AIに正解を出させる前に、何を重視するのかを決める必要がある。

評価基準がないままAIを導入すると、技術的にはそれらしい案が出ても、組織として採用してよいか判断しにくい。

この点は [AIがコードを書く時代に人間は何を確認するのか](/reports/ai-code-generation-human-checkpoints) や [システム化しても余裕をゼロにしない方がいい理由](/reports/system-efficiency-risk-buffer) とも関係する。

## AI導入前に確認したいこと

専門業務にAIを使う前に、次の点を確認したい。

| 観点 | 確認したいこと |
| --- | --- |
| 正解定義 | 何を正解とするか説明できるか |
| データ量 | 学習や評価に使える件数があるか |
| データ品質 | 古い、重複、欠落、入力ゆれがないか |
| データ形式 | AIやプログラムが読める形式にできるか |
| 権利と機密 | 学習や外部API利用に使ってよいデータか |
| 評価基準 | 出力を誰が、どの基準で評価するか |
| 失敗例 | 避けたい失敗や不採用例が残っているか |
| 運用 | 間違った出力を誰が確認し、修正するか |
| 費用 | データ整備、学習、推論、確認作業の費用が合うか |

特に重要なのは、学習データを用意する費用だ。

AIのAPI利用料やGPU費用よりも、データ整理、ラベル付け、形式変換、専門家レビューの方が重くなることがある。

## 小さな検証で見たいこと

最初から大規模に学習させる前に、小さな検証で次の点を確認したい。

- 代表的なデータを取り出せるか
- データ形式をそろえられるか
- 正解例を10件から50件程度作れるか
- 専門家が出力を評価できるか
- AIの間違い方にパターンがあるか
- データ追加で改善しそうか
- そもそもルールベースや検索で十分ではないか

AIを使う前に、まずデータを扱える状態にできるかを確認した方がよい。

ここでいう10件から50件程度は、それだけで十分に学習できるという意味ではない。まず、人間が正解例を作れるか、評価基準を説明できるか、データ形式をそろえられるかを確認するための最初の検証である。

この検証で、データを取り出せない、正解例を作れない、評価者が決まらない、という問題が見えた場合は、モデル選定より先にデータ整備や業務整理が必要になる。

これは [小さな検証（PoC）が成功しても本番導入できない理由](/reports/poc-success-production-adoption-risks) と同じで、小さな検証の目的は成功を演出することではなく、本番導入時の制約を早く見つけることだ。

## まとめ

AIに専門業務を任せるときに難しいのは、AIに処理させることだけではない。

何を正解として教えるかを用意することが難しい。

特に、3D、CAD、動画、音声、独自形式、社内固有ルール、暗黙知を含む業務では、学習データの量、形式、品質、評価基準をそろえる前処理が大きな負担になる。

LoRAやファインチューニングを使っても、お手本データが不要になるわけではない。既存AIが一般知識を持っていても、社内固有の文脈や専門家の判断基準は人間側で整理する必要がある。

AI導入では、モデルの性能だけでなく、正解データを作れるか、評価できるか、運用できるかを先に確認したい。

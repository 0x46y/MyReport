## 結論

公開されているLLMをPCへ入れただけでは、Claude Codeのような開発Agentの代わりにはならない。

LLM（エルエルエム・文章やコードを生成する大規模言語モデル）は、依頼を読んで回答を作る部分を担当する。一方、開発Agentは、プロジェクトのファイルを読み、変更し、コマンドやテストを実行し、その結果を見て再び修正する。

外部AIへの通信が禁止された環境で同様の開発支援を行うには、少なくとも次の三つが必要になる。

> ローカル開発Agent → ローカル推論ランタイム → コーディング向けLLM

推論ランタイムとは、モデルファイルを読み込み、PCのCPUやGPUを使って回答を生成する実行環境である。Ollamaなどがこの役割を担う。

この構成は技術的な候補にはなる。しかし、クラウド型の開発Agentと同じ品質、速度、導入のしやすさを保証するものではない。モデルの性能だけでなく、PC性能、長いコードの扱い、ツール呼び出し、権限、ライセンス、完全オフライン化を含めた小規模検証が必要である。

## この調査を行った理由

顧客先などでは、利用できるAIサービスが環境ごとに異なる。Claude Codeを利用できない場合でも、禁止理由は一つとは限らない。

- 特定のAI事業者への通信だけが禁止されている
- 外部の生成AI全般が禁止されている
- ソースコードを外部へ送信できない
- CLIやIDE拡張機能を追加できない
- インターネットへ接続できない
- 公開モデルやOSSの導入にも個別承認が必要である

特定サービスへの通信だけが禁止されているなら、組織が許可した別のクラウド型開発Agentが候補になる。外部AI通信そのものが禁止されている場合に、初めてローカルLLMが主要候補になる。

したがって、最初に「Claude Codeが使えない」とだけ確認するのでは不十分である。何が禁止され、何なら許可されるかを分けて確認する必要がある。

## LLMと開発Agentの違い

LLMとAgentは同じ意味ではない。

| 項目 | LLM | 開発Agent |
| --- | --- | --- |
| 主な役割 | 文章やコードを生成する | 開発作業を計画して進める |
| ファイル参照 | 入力として渡された内容を読む | 必要なファイルを探して読む |
| ファイル編集 | 修正案を文章として出せる | 実際のファイルへ変更を適用する |
| コマンド実行 | 単体では実行しない | ビルド、テスト、Gitなどを実行する |
| 結果の確認 | 利用者が結果を渡す | 実行結果を読み、次の修正を考える |
| 権限 | モデルへの入力管理が中心 | ファイル、コマンド、通信の許可も必要 |

たとえば、ローカルLLMへ「このエラーを直して」と質問すると、コード例や説明は返せる。しかし、プロジェクトのどのファイルに原因があるかを探し、実際に修正し、テストが通るまで繰り返すには、Agent側の機能が必要になる。

Ollamaの公式資料でも、モデルを動かす機能と、コードを読み書き・実行するコーディングAgentとの連携は分けて説明されている。2026年1月には、OllamaからClaude Code、OpenCode、Codexなどを設定・起動する仕組みも公開された。

- [Ollama: Coding Agentなどとの連携一覧](https://docs.ollama.com/integrations)
- [Ollama: ローカル／クラウドモデルでコーディングツールを起動する方法](https://ollama.com/blog/launch)

Qwen3-Coderもモデルだけでなく、ファイル操作やツール呼び出しを行うためのQwen CodeというCLIを別に公開している。ここからも、モデルとAgent実行基盤が別の構成要素であることが分かる。

- [Qwen: Qwen3-CoderとQwen Code](https://qwenlm.github.io/blog/qwen3-coder/)

## ローカル構成に必要なもの

### 1. コーディング向けLLM

自然言語の指示を理解し、既存コードを読み、修正案やツール呼び出しを出力するモデルが必要になる。

候補を選ぶときは、単純なコード生成の得点だけでなく、次を確認したい。

- 日本語の要求を正しく理解できるか
- 複数ファイルにまたがる変更を扱えるか
- 長いコードと指示を同時に保持できるか
- Agentが期待する形式でツールを呼び出せるか
- 修正後のテスト結果を読んで再修正できるか
- 利用目的と配布方法がモデルのライセンスに合うか

公開モデルとして入手できることと、自由な条件で業務利用できることも同じではない。モデルごとのライセンスと利用規約を確認する必要がある。

### 2. ローカル推論ランタイム

モデルを手元のPCで動かす環境が必要になる。OllamaはWindowsを含むローカル環境でモデルを動かし、ほかのツールが接続できるAPIを提供する選択肢の一つである。

Ollamaはツール呼び出しにも対応している。ツール呼び出しとは、モデルが回答文だけを返すのではなく、「このファイルを読む」「このコマンドを実行する」といった処理をAgentへ依頼するための形式である。

- [Ollama: Tool support](https://ollama.com/blog/tool-support)
- [Ollama: Windowsでのローカル実行](https://ollama.com/blog/windows-preview)

ただし、Ollamaをインストールしただけで完全オフラインになるわけではない。モデル取得、自動更新、テレメトリ、クラウドモデルへの切り替え、Agent側の通信を含めて確認する必要がある。

### 3. ローカル開発Agent

Agentは、LLMの指示と実際の開発環境をつなぐ。

主な役割は次のとおりである。

- プロジェクト内のファイルを検索する
- 必要なファイルをモデルへ渡す
- 差分を作成してファイルへ反映する
- ビルドやテストを実行する
- エラー出力をモデルへ返す
- Git差分を人が確認できる形にする
- 危険なコマンドの実行前に許可を求める

モデルの回答品質が高くても、Agentが必要なコードを選べなかったり、ツール呼び出しに失敗したりすれば、開発作業は進まない。逆に、Agentの操作機能が充実していても、モデルが小さすぎて要件やコードを理解できなければ、誤変更が増える。

## PC性能が判断に与える影響

ローカルLLMでは、モデルの大きさと一度に扱う情報量が、必要なメモリやVRAM（ブイラム・GPU専用メモリ）に影響する。

開発Agentでは、会話だけでなく、複数のソースコード、指示、ツールの説明、テスト結果を同時にモデルへ渡す。モデルが一度に扱える情報量はコンテキスト長と呼ばれる。長いコンテキストを設定すると、大きなプロジェクトを扱いやすくなる一方、必要メモリも増える。

Ollamaが2026年1月に公開したコーディングツール連携例では、64,000トークンのコンテキストを使う特定モデルについて約23GBのVRAMが必要と記載されている。これはすべてのモデルに共通する必要量ではないが、12GB程度のGPUでは、モデルサイズやコンテキストをそのまま使えない構成があることを示している。

以前のローカルLLM検証でも、軽量なGemma系モデルは起動できた一方、大きいモデルではタイムアウトや不自然に短い応答が発生した。これは開発Agentとしての比較試験ではないが、「モデルを取得できること」と「実用的に使えること」が別である具体例になった。

必要メモリを減らすため、モデル内部の数値表現を小さくする量子化という方法もある。ただし、量子化率を高くすると、回答品質やツール呼び出しの安定性に影響する可能性がある。容量だけで採用せず、実際の開発課題で確認したい。

## 完全オフラインで追加確認が必要なこと

「モデルをローカルで動かす」と「外部通信が一切ない」は同じではない。

完全オフライン環境を成立させるには、少なくとも次を確認する。

- モデル、Agent、推論ランタイム、依存パッケージを事前に取得できる
- インストール媒体を顧客環境へ持ち込む手続きがある
- 自動更新とクラウドへのフォールバックを停止できる
- テレメトリやエラー報告の送信先を確認できる
- AgentがWeb検索や外部APIを勝手に呼び出さない
- 必要なIDE、CLI、実行ファイルの導入が許可されている
- モデルとOSSのライセンス確認者が決まっている
- 脆弱性情報や更新版をオフライン環境へ反映する運用がある

ネットワークを遮断すれば終わりではない。更新できないことにより、脆弱性対応やモデル差し替えが遅れる可能性も運用リスクになる。

## Agentへ与える権限を決める

ローカル実行であっても、Agentへ無制限の権限を与えてよいわけではない。

Agentがファイル編集とコマンド実行を行えるなら、誤った指示やモデルの誤判断によって、必要なファイルを変更したり、機密情報をログへ出したりする可能性がある。

導入時には、次を決めておきたい。

| 権限 | 確認事項 |
| --- | --- |
| ファイル参照 | 対象プロジェクト外を読めないようにできるか |
| ファイル編集 | 差分確認前に自動反映する範囲はどこか |
| コマンド実行 | 実行前の承認が必要なコマンドは何か |
| ネットワーク | 外部接続を許可するか、遮断するか |
| 認証情報 | APIキーや秘密情報へアクセスさせない方法があるか |
| Git操作 | コミット、push、PR作成を自動化するか |

少なくとも導入初期は、人が差分を読み、テスト結果を確認してから採用する運用が必要である。

## 候補を同じ条件で比較する

今回の調査は、公開資料から構成と候補を整理した段階であり、ローカル開発Agentの実機比較は行っていない。したがって、特定のモデルやAgentを採用候補として確定することはできない。

実機検証を行う場合は、非機密の小さなリポジトリを用意し、クラウド型とローカル型へ同じ課題を与える。

たとえば、次のような課題が使える。

> 既存の小規模Webアプリへ入力項目を一つ追加し、保存処理、入力検証、自動テスト、説明文を更新する。

比較する項目は次のとおりである。

- 要件を正しく理解できたか
- 必要なファイルを自分で見つけられたか
- 完成までに人が何回介入したか
- ビルドと自動テストが成功したか
- 不要なファイルや機能を変更していないか
- 認証情報や危険なコマンドを扱っていないか
- 最初の回答までと完成までに何分かかったか
- RAM、VRAM、ディスクをどの程度使用したか
- 完全オフライン状態でも同じ処理を完了できたか

「コードを書けたか」だけではなく、調査、編集、テスト、再修正まで完了できたかを見る。

## 現時点の判断

顧客環境ごとの候補は、次のように整理できる。

| 制約 | 最初に検討する候補 |
| --- | --- |
| 特定のAIサービスだけ禁止 | 組織が許可する別のクラウド型開発Agent |
| CLI追加は禁止、既存IDE拡張は利用可能 | 許可済みIDEのAgent機能 |
| ソースコードの外部送信は禁止 | ローカルAgent＋ローカル推論＋公開モデル |
| インターネット接続が全面禁止 | 事前取得した完全オフライン構成 |
| ローカルPCの性能が不足 | 管理された社内GPUサーバー、またはAIを使わない従来開発 |

ローカルLLMは、外部AI通信が禁止された環境での有力な調査候補である。ただし、「無料のモデルを入れればClaude Codeと同じになる」という選択肢ではない。

モデル、推論環境、Agent、ハードウェア、権限、更新運用を一つのシステムとして評価する必要がある。また、導入と保守にかかる時間まで含めると、従来の開発方法を続ける方が合理的な場合もある。

## まとめ

公開LLMは、クラウド型開発Agentのモデル部分を置き換える候補にはなる。しかし、モデル単体ではファイル編集、コマンド実行、テスト、権限確認を行えない。

ローカル代替を検討するときは、次の順序で考えたい。

1. 何が禁止されているかを確認する
2. ローカル構成が本当に必要かを判断する
3. LLM、推論ランタイム、Agentを分けて選ぶ
4. PC性能と完全オフライン条件を確認する
5. Agentの権限と人のレビュー範囲を決める
6. 非機密の同一課題でクラウド型と比較する

ローカルで起動できたことは検証の開始地点であり、採用判断ではない。実際のプロジェクトを安全に読み、修正し、テストまで完了できることを確認して、初めて開発Agentの代替候補として評価できる。

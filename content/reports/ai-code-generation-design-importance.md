結論から言うと、AIでコードを書きやすくなるほど、設計の重要性は下がるのではなく、むしろ前に出てくる。

AIは、一覧画面、登録画面、編集画面、DB操作、API、テストのたたき台をかなり速く作れる。さらに、Next.jsアプリ、Cloudflare Workers構成、D1スキーマ、認証機能、CRUD画面、CI/CD設定のような周辺構成まで提案できるようになっている。

一方で、どのデータを持つべきか、誰が編集できるべきか、削除してよいのか、障害時にどう戻すのか、業務ルールのどこまでを自動化するのかは、コード生成だけでは決められない。

この記事では、AIコーディングを使う時代に、なぜ設計、業務理解、運用条件の整理が重要になるのかを整理する。

CRUD、DB、権限管理、バックアップ、非機能要件などの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## AIは実装を速くするが、前提までは決めない

AIに依頼すると、画面やAPIのコードはかなり速く生成できる。

たとえば、次のような依頼は通りやすい。

- 施設一覧画面を作る
- 検索フォームを作る
- 登録、編集、削除のAPIを作る
- PrismaでDB操作を書く
- 管理画面のUIを作る
- 入力チェックを追加する
- Cloudflare Workersの設定を作る
- D1やR2とつなぐ構成を提案する
- 認証機能のたたき台を作る
- GitHub Actionsやデプロイ手順を作る

これらは実装としては重要だ。

しかし、実際の業務システムでは、コードを書く前に決めることが多い。

- 施設とは何を指すのか
- 住所、担当者、連絡先、公開状態をどう持つのか
- 削除は物理削除か、非表示か
- 誰が編集できるのか
- 更新履歴を残すのか
- CSVで取り込めるようにするのか
- 間違って登録したときに戻せるのか

AIは候補を出せるが、業務上どれが正しいかは人間が決める必要がある。

## CRUDは作りやすいが、業務ルールで難しくなる

CRUDは、データを登録、表示、更新、削除する基本操作だ。

AIを使うと、CRUDアプリのたたき台はかなり速く作れる。

しかし、業務システムで難しいのは、CRUDそのものより、CRUDの周辺にある業務ルールだ。

| 観点 | 単純なCRUD | 実際の業務システム |
| --- | --- | --- |
| 登録 | 入力したデータを保存する | 重複、必須項目、入力形式、承認を確認する |
| 表示 | 一覧に出す | 公開範囲、権限、並び順、検索条件を決める |
| 更新 | 値を変更する | 誰が変更したか、履歴を残すかを決める |
| 削除 | レコードを消す | 非表示にするのか、復元できるのかを決める |
| 連携 | APIを呼ぶ | 失敗時、再試行、料金、責任範囲を決める |

AIがCRUDを作れることと、業務で安全に使えることは別だ。

ここを分けないと、「動いたが運用できない」アプリになりやすい。

## データ設計は後から直すほど重くなる

AIに画面から作らせると、見た目はすぐにできる。

しかし、画面の裏側にあるデータ設計が曖昧なままだと、後から変更が重くなる。

たとえば、最初は1つのテーブルで十分に見えても、後から次のような話が出ることがある。

- 1つの施設に複数の担当者を持たせたい
- 担当者ごとに権限を分けたい
- 住所と表示名を別に管理したい
- 変更履歴を残したい
- 公開用データと内部用データを分けたい
- 外部システムのIDと紐づけたい

この段階でDB構造を変えると、画面、API、バリデーション、既存データ、テスト、移行処理まで影響する。

AIは修正コードを出せるが、データ移行や運用中データの整合性まで自動で保証してくれるわけではない。

だから、最初から完璧な設計をする必要はないが、少なくとも「後から変わりそうな部分」は意識しておきたい。

記事サイトでも同じことがある。

最初はMarkdownファイルだけで十分に見えても、後から下書き管理、公開状態、カテゴリ、タグ、画像管理、関連記事、ロードマップ、複数サイト展開を扱いたくなることがある。

この場合、単に管理画面を追加すれば終わりではない。記事本文をMarkdownのまま持つのか、DBへ移すのか、画像をどこへ保存するのか、AIに記事全体を読ませやすい状態を残すのかを決める必要がある。

この点は [静的サイトをCMS化する前に確認したいこと](/reports/static-site-before-cms-migration) とも関係する。

## 権限は後付けすると手戻りが大きい

小さな試作品では、全員が同じ画面を見て、同じ操作ができる状態でも問題にならないことがある。

しかし、本番運用に近づくと、権限管理が必要になる。

たとえば、

- 誰でも閲覧できる情報
- ログインした人だけ見られる情報
- 管理者だけ編集できる情報
- 一般担当者は登録できるが削除できない情報
- 公開前に承認が必要な情報

を分けたくなる。

権限を後から入れる場合、単にログイン画面を足せば終わりではない。

画面、API、DB、エラーメッセージ、監査ログ、テスト、運用手順まで見直す必要がある。

AIで実装は速くなっても、「誰が何をしてよいか」という判断は先に整理した方がよい。

## 運用・バックアップ・障害対応も設計に含まれる

設計というと、画面設計やDB設計を思い浮かべやすい。

しかし、業務システムでは運用も設計に含めて考えたい。

確認したいこと:

- 誰が日常的にデータを更新するか
- 誤って削除したときに戻せるか
- バックアップはどこにあるか
- 障害時に誰へ連絡するか
- ログを見て原因を追えるか
- 手動運用へ一時的に切り替えられるか
- 管理者が変わったときに引き継げるか

このあたりは、AIに「管理画面を作って」と頼んだだけでは抜けやすい。

実装ではなく、運用の前提として人間が決める必要がある。

この点は [システム化しても余裕をゼロにしない方がいい理由](/reports/system-efficiency-risk-buffer) とも関係する。

## AIに渡す前に決めたいこと

AIにコードを書かせる前に、次のような情報を整理しておくと、出てくるコードの質も上がりやすい。

| 観点 | AIに渡したい情報 |
| --- | --- |
| 目的 | 何を楽にしたいのか |
| 利用者 | 誰が使うのか |
| 更新者 | 誰がデータを登録、編集するのか |
| データ | どの項目を持つのか、必須項目は何か |
| 権限 | 誰が閲覧、編集、削除できるか |
| 運用 | 誰が保守し、障害時に誰が見るか |
| 制約 | 使ってよいクラウド、DB、外部API、予算 |
| 除外範囲 | 今回は作らない機能 |

この情報がないままAIに依頼すると、AIは一般的な構成を出す。

しかし、一般的な構成が、その業務に合うとは限らない。

AIに任せるほど、依頼する前の整理が重要になる。

## 試作品は設計の粗さを見つける道具になる

設計をすべて紙の上で固める必要はない。

小さな試作品を作ることで、設計の足りない部分が見えることもある。

たとえば、CRUD画面を作ってみると、次のようなことが分かる。

- 入力項目が多すぎる
- 検索条件が足りない
- 削除より非表示の方が安全
- スプレッドシート運用では壊れやすい
- 管理画面が必要な範囲が見えてくる
- 権限管理が必要な操作が分かる

つまり、試作品は完成品ではなく、設計を見直すための判断材料になる。

この点は [試作品は完成品ではなく判断材料になる](/reports/prototype-communicates-better-than-proposal) ともつながる。

## 設計はAIへの制約指定でもある

設計は、AIに対する制約指定でもある。

たとえば、

```text
施設情報を登録、検索、編集できる管理画面を作ってください。
削除は物理削除ではなく非表示にしてください。
管理者だけが編集できます。
CSV出力は必要ですが、CSV取り込みは今回は作りません。
DBはPostgreSQLを想定してください。
将来、施設ごとに担当者を複数持てるようにしたいです。
```

このように伝えると、AIは設計意図に沿ったコードを出しやすくなる。

逆に、

```text
施設管理アプリを作ってください。
```

だけだと、AIは一般的な施設管理アプリを推測して作る。

動くものはできるかもしれないが、後から業務ルールを入れると手戻りが大きくなる。

## 確認したいこと

AIでコードを書く前に、少なくとも次の点を確認したい。

| 観点 | 確認したいこと |
| --- | --- |
| データ設計 | 何を保存し、何を保存しないか |
| 権限 | 誰が閲覧、登録、編集、削除できるか |
| 削除 | 物理削除か、非表示か、復元できるか |
| 履歴 | 誰がいつ変更したか残すか |
| 運用 | 誰が日常的に更新し、誰が保守するか |
| 例外 | 入力ミス、重複、空欄、外部データをどう扱うか |
| 本番化 | 監視、ログ、バックアップ、障害対応をどうするか |
| 費用 | DB、ストレージ、AI API、クラウド実行時間が増えないか |
| 撤退条件 | どこまで作って、どこで別案に切り替えるか |

AIで実装できるかどうかだけでなく、業務として運用できるかを見たい。

## まとめ

AIでコードを書ける時代になると、実装の速度は上がる。

しかし、データ設計、権限、運用、バックアップ、障害対応、業務ルールの判断は残る。

むしろ、AIが画面やCRUDを速く作れるからこそ、何を作るべきか、どこまで作るべきか、何を後回しにするかを先に決める重要性が増す。

設計は、AI時代に不要になる作業ではない。

AIに現実的なコードを書かせるための前提条件であり、発注者、利用者、開発者が同じものを見ながら判断するための土台になる。

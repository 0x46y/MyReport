結論から言うと、技術者が決めることと、業務担当者が決めることは分けて考えた方がよい。

技術者は、DB設計、API、画面、権限、ログ、バックアップ、連携処理を設計できる。一方で、この住所が正しいか、この価格で販売してよいか、このAIの回答を採用してよいか、この契約書を公開してよいかは、技術だけでは判断できない。

ここを曖昧にすると、開発者が業務上の正しさまで背負ったり、業務側が「システムに入っているから正しいはず」と考えたりしやすい。

この記事では、業務システム開発で、技術者が判断できることと、業務担当者や管理者が判断すべきことを整理する。

DB、API、権限管理、責任分界点、CRUDなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 技術者は仕組みを作れるが、業務上の正しさは別に決める必要がある

業務システムでは、技術者が多くの仕組みを作る。

たとえば、次のようなものだ。

- データを登録する画面
- データを検索する画面
- API連携
- CSV取込
- 権限管理
- 変更履歴
- バックアップ
- エラー通知
- AIによる分類や候補提示

これらは重要だ。

しかし、仕組みを作れることと、業務上の判断をできることは違う。

たとえば、住所を保存するDBは作れる。住所の入力チェックも作れる。郵便番号から住所を補完する機能も作れる。

しかし、「この住所が本当に正しいか」「どの住所を正式なものとして扱うか」「間違いを指摘されたとき誰が確認するか」は、業務側の判断が必要になる。

技術者は、正しいデータを入れやすくし、間違いに気づきやすくし、修正しやすくする仕組みを作れる。

ただし、業務上の正しさそのものを単独で保証できるわけではない。

## 技術者が決めやすいこと

技術者が主に判断しやすいのは、システムの構造や実装方法に関することだ。

たとえば、次のような判断がある。

| 項目 | 技術者が判断しやすいこと |
| --- | --- |
| DB設計 | どのテーブルに分けるか、どの項目を持つか |
| API | どのデータをどの形式で受け渡すか |
| 画面 | 入力、検索、編集、確認をどう操作できるようにするか |
| 権限 | 誰が閲覧、編集、削除、承認できるようにするか |
| ログ | 誰がいつ何を変更したかをどう記録するか |
| バックアップ | どの頻度で保存し、どの範囲を復旧できるようにするか |
| エラー処理 | 入力ミス、通信失敗、外部API停止時にどう通知するか |
| 性能 | データ量や同時アクセスにどこまで対応するか |

これらは、技術者が提案し、設計し、実装しやすい領域である。

ただし、技術者だけで完結するわけではない。

たとえば、「削除できるようにするか」は技術的には実装できる。しかし、削除してよい業務データなのか、履歴として残す必要があるのかは業務側と確認する必要がある。

## 業務担当者や管理者が決めること

一方で、業務担当者や管理者が判断すべきこともある。

たとえば、次のようなものだ。

| 項目 | 業務側が判断すべきこと |
| --- | --- |
| 正式な値 | どの住所、価格、契約条件、名称を正とするか |
| 公開可否 | その情報を社外や利用者に公開してよいか |
| 承認 | 誰が確認したら正式な情報として扱うか |
| 例外対応 | 通常ルールに当てはまらない場合にどう扱うか |
| AI結果 | AIの分類、要約、提案を採用してよいか |
| 優先順位 | どの機能や修正を先に扱うか |
| 取引条件 | 価格、契約、納期、責任範囲をどう決めるか |
| 業務ルール | 現場で許容される運用か、社内ルールに合うか |

これらは、技術的に画面やDBで表現できても、判断自体は業務知識や組織上の責任に関係する。

たとえば、商品価格を保存する画面は作れる。しかし、その価格で販売してよいかは、営業、管理者、契約担当などが判断する必要がある。

AIが問い合わせの回答案を作ることはできる。しかし、その回答を利用者へ送ってよいかは、業務担当者や責任者が確認する必要がある。

## 業務担当者も技術判断を背負わなくてよい

逆に、業務担当者が技術判断をすべて背負う必要もない。

たとえば、業務担当者は「検索が遅い」「一覧画面で探しにくい」「入力ミスを減らしたい」「外出先でも確認したい」といった困りごとを伝えられる。

しかし、その解決方法として、DBにインデックスを追加するのか、検索条件を変えるのか、キャッシュを使うのか、画面構成を変えるのか、クラウド構成を見直すのかは、技術者が判断した方がよい領域である。

業務担当者が「この画面を速くしてほしい」と言うことはできる。

ただし、Redisを使うべきか、RDBの設計を変えるべきか、SQLを最適化するべきか、別の実行環境へ移すべきかまでは、技術者が条件を見て提案する必要がある。

つまり、業務側は問題、制約、優先順位を伝える。技術側は実装方法、構成、リスク、代替案を整理する。

どちらか一方がすべてを決めるのではなく、お互いの専門分野を持ち寄る形にした方が、現実的な判断をしやすい。

## 技術者が業務判断まで背負うと何が起きるか

技術者が業務判断まで背負う形になると、いくつかの問題が起きやすい。

- 正しい業務ルールが分からないまま実装する
- 現場ごとの例外を知らずに固定ルールにしてしまう
- 誰も承認していない値を正式データとして扱う
- AIの出力を誰も確認しないまま使う
- 問い合わせが来たとき、開発者が業務上の正しさまで説明することになる
- 障害時に、技術的復旧と業務上の復旧判断が混ざる

これは、技術者が無責任という話ではない。

技術者が持っている情報と、業務担当者が持っている情報が違うという話である。

技術者は、実装方式、データ構造、ログ、復旧方法を説明できる。一方で、業務担当者は、どの情報が正しいか、どの例外を許すか、誰に確認すべきかを知っている。

この2つを分けておかないと、システム上は動いているのに、業務としては危ない状態になりやすい。

## 発注側も「何を決める必要があるか」を知っておきたい

この話は、開発者だけの問題ではない。

発注側や利用者側も、「開発者に任せること」と「自分たちが決めること」を分けておくと相談しやすい。

たとえば、開発者へ次のように依頼することはできる。

```text
施設情報を登録、編集、検索できる管理画面を作ってほしい。
変更履歴を残し、削除は管理者だけができるようにしたい。
```

一方で、次のことは業務側で決める必要がある。

```text
どの施設情報を正式な情報として扱うか。
誰が公開前に確認するか。
間違いを指摘されたとき誰が修正判断をするか。
古い情報を削除するのか、非表示にするのか。
```

ここが決まっていないと、開発者は画面を作れても、受け入れ条件を決めにくくなる。

発注側と開発側で、先に言葉をそろえておくことが重要になる。

この点は [システム開発を依頼するときに最初に決めたいこと](/reports/requesting-system-development-first-decisions) とも関係する。

## AIが入ると境界がさらに曖昧になる

AIを使うと、業務判断の境界がさらに曖昧になりやすい。

AIは、分類、要約、文章作成、候補提示、コード生成、画像生成などを行える。

しかし、AIの出力をどこまで採用してよいかは別の判断になる。

確認したいこと:

- AIの出力は候補なのか、確定値なのか
- 人間の確認を必須にするか
- 誤った出力が出た場合、誰が修正するか
- 利用者へ表示してよい情報か
- 機密情報や個人情報をAIへ入力してよいか
- AIが出した判断を記録する必要があるか

たとえば、AIが「この問い合わせは緊急度が高い」と分類したとする。

技術者は、その分類結果を画面に表示したり、通知したりできる。

しかし、それを本当に緊急扱いにするか、誰に連絡するか、誤判定時にどう対応するかは、業務側の判断が必要になる。

AIを使うほど、技術的に出せる結果と、業務として採用してよい結果を分けて考えたい。

この点は [AIがコードを書く時代に人間は何を確認するのか](/reports/ai-code-generation-human-checkpoints) や [AIに専門業務を教える前に確認したい学習データの問題](/reports/ai-training-data-for-specialized-work) ともつながる。

## 境界を曖昧にしないための確認表

業務システムを作るときは、次のように「誰が決めるか」を整理しておくとよい。

| 判断項目 | 技術者が決めること | 業務側が決めること |
| --- | --- | --- |
| 住所情報 | 入力形式、必須チェック、履歴 | どの住所を正式なものとするか |
| 商品価格 | DB項目、変更履歴、権限 | 価格、適用日、承認者 |
| 公開情報 | 公開フロー、プレビュー、権限 | 公開してよい内容か |
| AI分類 | 分類結果の保存、表示、ログ | 採用してよい分類か、確認者は誰か |
| 削除 | 論理削除、復旧、権限 | 削除してよい条件 |
| 障害対応 | ログ、復旧手順、バックアップ | 業務を止めるか、手動運用へ切り替えるか |

この表を作る目的は、責任を押し付け合うことではない。

曖昧な判断を見えるようにし、誰に確認すればよいかを明確にするためである。

## 技術者が言えるとよいこと

技術者は、業務判断を勝手に背負うのではなく、次のように説明できると話が進みやすい。

```text
技術的には、この画面で登録、編集、公開できます。

ただし、公開してよい情報かどうかは業務側の確認が必要です。
そのため、下書き、確認済み、公開済みの状態を分ける設計にできます。
```

あるいは、

```text
AIで分類候補を出すことはできます。

ただし、誤分類時の責任範囲を考えると、
最初は人間が確認して確定する運用にした方がよいです。
```

このように説明すると、「できない」と言っているのではなく、業務判断を安全に扱うための設計案を出していることが伝わりやすい。

## まとめ

技術者が決めることと、業務担当者が決めることは分けて考えたい。

技術者は、DB、API、画面、権限、ログ、バックアップ、AI連携を設計できる。一方で、どの情報が正しいか、公開してよいか、AIの結果を採用してよいか、価格や契約条件をどう扱うかは、業務側の判断が必要になる。

これは、技術者が責任を避けるための話ではない。

技術と業務で見ているものが違うため、判断する人、承認する人、運用する人を先に分けておくという話である。

境界が明確になるほど、開発者は安全な仕組みを作りやすくなり、業務側も何を確認すればよいか分かりやすくなる。

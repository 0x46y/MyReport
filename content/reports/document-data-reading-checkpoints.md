結論から言うと、資料やデータを見るときは、数字そのものだけでなく、誰が、何の目的で、どの条件で作ったのかも確認した方がよい。

表やグラフがあると、客観的な情報に見えやすい。AIに要約させても、数字や見出しが整っていれば、それらしく整理してくれる。しかし、資料には作成者の目的、集計条件、強調したい点、あまり目立たせたくない点が含まれることがある。

この記事では、資料、KPI、提案書、障害報告、公開データ、AIの要約結果を見るときに確認したいことを整理する。

KPI、CSV、AI、PoCなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## データと事実は同じではない

データは事実を理解するための材料になる。

ただし、データそのものが事実のすべてを表しているわけではない。

たとえば、次のような資料があったとする。

| 年 | 障害件数 |
| --- | --- |
| 2025年 | 10件 |
| 2026年 | 2件 |

この表だけを見ると、障害が大きく減ったように見える。

しかし、次の条件が変わっているかもしれない。

- 障害の定義を変えた
- 軽微な障害を集計対象から外した
- 報告対象のシステムが変わった
- 利用者数や処理量が減った
- 検知できていない障害が増えた

この場合、数字自体は間違っていなくても、「改善した」と判断してよいかは別の話になる。

重要なのは、数字を疑うことではない。数字を判断材料として使う前に、集計条件を確認することだ。

## 何が強調され、何が小さく扱われているかを見る

資料には、必ず見せ方がある。

同じデータでも、表の順番、グラフの軸、見出し、注釈、文字の大きさ、ページ配置によって印象は変わる。

たとえば、ある報告書で次のような構成になっていることがある。

- 問題点は大きな見出しで説明されている
- 改善点は小さな注釈に入っている
- 都合のよい期間だけがグラフになっている
- 注意書きが多く、肝心の数字を追いにくい
- 前提条件が最後のページにまとめられている

これは必ずしも悪意とは限らない。

丁寧に説明しようとした結果、注意書きが多くなることもある。法務や監査の都合で注釈が増えることもある。複雑な内容を正確に伝えようとして、資料が読みにくくなる場合もある。

ただし、読む側としては、次の点を確認したい。

- どの数字が大きく見せられているか
- どの数字が小さく扱われているか
- 比較対象は妥当か
- 期間の切り方は妥当か
- グラフの軸や単位は変わっていないか
- 注釈や前提条件はどこにあるか

資料を読むときは、書かれていることだけでなく、目立たない場所に置かれている情報も見る必要がある。

## AIは表や数字を読めるが、作成意図までは保証しない

AIは、長い資料を要約したり、表を読み取ったり、グラフの傾向を説明したりできる。

これはかなり便利だ。

しかし、AIが資料を読めることと、その資料の作成意図や利害関係まで正しく判断できることは別だ。

AIは、次のような情報に引っ張られやすい。

- 文章量が多い箇所
- 見出しになっている箇所
- 表やグラフになっている箇所
- 公式資料らしく見える体裁
- 繰り返し書かれている注意書き

一方で、人間なら違和感を持つような点を見落とすことがある。

- なぜこの期間だけを比較しているのか
- なぜこの指標だけが強調されているのか
- なぜ別の指標が出てこないのか
- なぜ注釈がこの位置にあるのか
- なぜ元データが公開されていないのか

AIに資料を要約させる場合でも、「この資料は何を強調しているか」「扱っていない情報は何か」「前提条件はどこにあるか」を別途確認したい。

## 業務資料でも同じことが起こる

これは政治や報道の話だけではない。

業務の中でも、資料の見せ方によって印象が変わることはよくある。

たとえば、プロジェクト報告で「進捗率90%」と書かれている場合でも、その残り10%が何を意味するかで判断は大きく変わる。

| 残り10%の中身 | 判断 |
| --- | --- |
| ボタンの文言修正 | 予定通り終わる可能性が高い |
| 外部API連携 | 追加調査が必要かもしれない |
| 本番データ移行 | 失敗時の影響が大きい |
| 権限設計 | 後から直すと大きく戻る可能性がある |
| 性能問題 | 本番導入時期に影響する可能性がある |

同じ「90%完了」でも、残っている作業の種類が違えばリスクは違う。

障害報告でも同じだ。

障害件数が減っていても、重大障害が増えているかもしれない。復旧時間は短くなっていても、暫定対応が増えているかもしれない。利用者数が減ったために障害件数が減って見えているだけかもしれない。

数字を見るときは、件数だけでなく、影響範囲、重大度、復旧時間、再発防止、対象システム、集計条件も合わせて見たい。

## 表形式の資料は人間向けと機械向けで違う

Excelやスプレッドシートの記事でも整理したように、表形式の資料には二つの性格がある。

一つは、人間が読むための資料だ。

色、結合セル、説明行、注意書き、空行、コメントを使って、人間が理解しやすいように作られる。

もう一つは、機械が読むためのデータだ。

列名、型、必須項目、行の単位、文字コード、空欄、重複が安定している必要がある。

この二つを混同すると問題が起きやすい。

人間向けの表をAIやプログラムにそのまま読ませると、注意書き、見出し行、結合セル、空行をデータとして扱ってしまうことがある。逆に、機械向けのデータだけを人間に見せると、背景や注意点が伝わりにくいことがある。

そのため、資料を読むときは、これは人間向けの説明資料なのか、機械処理を前提にしたデータなのかを分けて見たい。

この点は [業務システムでExcelやスプレッドシートがなくならない理由](/reports/why-excel-spreadsheets-remain-business-systems) とも関係する。

## 確認したいこと

資料やデータを見るときは、少なくとも次の点を確認したい。

| 観点 | 確認したいこと |
| --- | --- |
| 作成者 | 誰が作った資料か |
| 目的 | 何を判断してもらうための資料か |
| 対象範囲 | どの期間、部署、システム、利用者を含むか |
| 集計条件 | 何を数え、何を除外しているか |
| 定義 | 障害、完了、売上、利用者などの定義は何か |
| 比較対象 | 比較している期間や対象は妥当か |
| 単位 | 円、件、人数、割合、月額、年額が混ざっていないか |
| 見せ方 | グラフ軸、色、順番、注釈で印象が変わっていないか |
| 欠けている情報 | 出ていない指標や元データはないか |
| 影響 | この資料をもとに何を決めるのか |

資料を読む目的は、相手を疑うことではない。

判断に使う前提をそろえることだ。

## AIに要約させるときに追加したい指示

AIに資料を要約させるときは、単に「要約して」と頼むだけでは足りないことがある。

たとえば、次のような指示を加えると確認しやすい。

```text
この資料を要約してください。
あわせて、次の点も整理してください。

- 何を強調している資料か
- 前提条件や注釈はどこにあるか
- 集計条件は明示されているか
- 扱っていない指標や不足している情報はあるか
- この資料だけでは判断できないことは何か
- 追加で確認すべき元データや関係者は誰か
```

AIは大量の資料を読む補助として有効だ。

ただし、AIの要約結果もまた判断材料の一つであり、最終判断そのものではない。

この点は [AIがコードを書く時代に人間は何を確認するのか](/reports/ai-code-generation-human-checkpoints) ともつながる。

## まとめ

資料やデータを見るときは、数字があることだけで安心しない方がよい。

確認したいのは、数字そのものだけではなく、作成目的、集計条件、定義、比較対象、見せ方、欠けている情報だ。

表やグラフは判断材料になる。一方で、作り方によって印象が変わる。

AIに資料を読ませる場合も同じだ。AIは要約や抽出を助けてくれるが、資料の前提、作成意図、抜けている情報、判断への影響は人間が確認したい。

業務システムや技術調査では、データを読む力も重要になる。

何が書かれているかだけでなく、何を判断するための資料なのか、何が書かれていないのかを確認することで、資料をより安全な判断材料として使いやすくなる。

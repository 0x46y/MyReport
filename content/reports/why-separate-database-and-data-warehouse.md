結論から言うと、通常のデータベースとデータウェアハウスを分ける理由は、同じデータを二重に持ちたいからではない。守るべき処理が違うからだ。

注文、決済、在庫更新などは、今この瞬間の1件を正しく、短時間で処理する必要がある。一方、経営レポートや売上分析では、長期間の大量データをまとめて読み、条件を変えながら集計する。この2つを同じ基盤で無理に処理すると、分析が本番業務を遅らせることがある。

業務処理用DBは「現在の業務を回す基盤」、データウェアハウスは「過去を比較して判断するための記憶基盤」と捉えると分かりやすい。

## 最初に判断したいこと

すべてのシステムにデータウェアハウスが必要なわけではない。導入を考える前に、次の条件を確認したい。

| 確認項目 | 判断への影響 |
| --- | --- |
| 分析が本番DBを遅くしているか | 負荷を分離する必要性が高い |
| 複数部署の数字が一致しているか | データ定義を統合する必要がある |
| 過去時点の状態を再現できるか | 履歴を別に保持する必要がある |
| 何行、何年分を集計するか | 列指向や分散処理の効果が変わる |
| どの程度新しいデータが必要か | 連携頻度と費用が変わる |
| 誰が品質、権限、費用を管理するか | 導入後の運用体制が変わる |

月次集計が数秒で終わり、分析対象も単一DBに収まる小規模システムなら、最初からDWHを追加する必要はない。読み取り用の複製、集計済みテーブル、定期CSV出力で足りる場合もある。

## 業務処理と分析では、データの読み方が違う

注文登録を例にすると、業務処理用DBは特定の注文、顧客、在庫を素早く読み書きする。更新途中で数字が食い違わないことも重要になる。このような処理はOLTP（オーエルティーピー・日々の取引処理）と呼ばれる。

分析では「過去3年の全注文から、月別、地域別、商品分類別の売上を出す」のように、多数の行をまとめて読む。このような処理はOLAP（オーラップ・大量データの集計や分析）と呼ばれる。

| 観点 | 業務処理用DB（OLTP） | 分析基盤（OLAP） |
| --- | --- | --- |
| 主な役割 | 注文、決済、在庫などを処理する | 履歴を集計し、傾向を比較する |
| よくある処理 | 少数行の検索、追加、更新 | 大量行の走査、集計、比較 |
| 優先すること | 低遅延、整合性、同時更新 | 読み取り性能、履歴、分析しやすさ |
| データ設計 | 重複を減らし、更新矛盾を防ぐ | 結合や集計を減らす形も使う |
| 時間の見方 | 現在の正しい状態 | 過去から現在までの変化 |

業務DBでは、顧客名を顧客テーブルに1回だけ持たせるように、重複を減らして整合性を守る設計がよく使われる。これを正規化という。一方、分析側では、何度も複雑な表の結合をしなくてよいように、分析しやすい形へ組み直すことがある。

代表例が、売上金額や数量を持つファクトテーブルを中心に置き、日付、商品、店舗などの分析条件をディメンションテーブルとして周囲に置くスタースキーマである。

## 分析を本番DBで実行すると何が起きるか

本番稼働中のDBに月末集計を直接実行すると、CPU、メモリ、ディスク入出力、接続数を分析処理が使う。その結果、注文画面の表示や決済処理が遅れる可能性がある。

読み取り専用の複製であるリードレプリカを使えば、本番DBとの負荷分離には役立つ。ただし、複製されるテーブル構造は基本的に業務処理向けのままである。大量集計に必要な履歴がなく、複雑な結合が多いなら、レプリカを置くだけでは分析の遅さやデータ定義の不一致は解決しない。

つまり、問題を二つに分けて考える必要がある。

- 本番処理と分析処理の計算負荷を分ける
- 分析に必要な履歴、共通定義、検索しやすい構造を用意する

DWHは後者まで含めた仕組みである。

## DWHは会社の履歴と定義をそろえる

データウェアハウスという考え方は、部門ごとに別々の集計を作り、同じ「売上」でも数字が合わなくなる問題への対応として発展した。

売上を注文時点で数えるのか、出荷時点か、入金時点か。返品や値引きをどう扱うのか。通貨換算はどの時点のレートを使うのか。データを1か所へコピーするだけでは、この違いは解消しない。

DWHには、一般に次の役割が求められる。

- 顧客、商品、売上など、分析対象ごとにデータを整理する
- 部署やシステムごとに異なる表記、単位、識別子を統合する
- 過去の履歴を保持し、時点ごとの変化を追えるようにする
- 元データが更新されても、必要な分析履歴を再現できるようにする

重要なのは保存場所より、定義と責任である。「売上」の定義を誰が決め、変更を誰が承認し、欠損や重複を誰が直すのかまで決めなければ、DWHを作っても数字への不信は残る。

## 列指向が大量集計に向く理由

業務DBでは、1件の注文に含まれる注文番号、顧客番号、日時、金額などをまとめて扱いやすい行指向の保存が一般的である。

分析では、何億件の注文があっても「金額」と「日付」だけを読むことがある。列指向では同じ列の値をまとめて保存するため、必要な列だけを読みやすい。同じ種類の値が並ぶので圧縮もしやすく、読み取るデータ量を減らせる。

2005年のC-Store論文は、更新中心の従来型DBと対比し、読み取り中心の用途に向けた列指向DBの設計を示した。現在のBigQueryなどの分析基盤でも、列単位の保存と大規模な並列処理が重要な仕組みになっている。

ただし、列指向なら常に速いわけではない。小量データの1件更新、対象列が多い検索、不適切なパーティション設計では利点が小さくなる。実際のクエリとデータ量で検証する必要がある。

## クラウドで変わったのは導入方法と費用構造

従来のDWHは、専用機器を購入し、将来の最大負荷を見越して容量を用意する構成が中心だった。クラウド型DWHでは、保存領域と計算資源を独立して増減できる製品が増え、小規模な検証を始めやすくなった。

たとえばBigQueryは保存と計算を分離した構成を採用し、Snowflakeも中央の保存領域と複数の計算クラスタを分けている。分析を実行しない時間に計算資源を停止できるサービスもある。

ただし「停止中は完全に無料」とは限らない。計算資源を止めても、データ保存、転送、バックアップ、データ連携、監視などの費用は残り得る。見るべきなのは導入価格だけではなく、次の運用費である。

- 保存量と保持期間
- クエリ量、実行時間、同時実行数
- 業務DBからデータを移す頻度
- 失敗した連携の再実行と監視
- 権限管理、監査ログ、個人情報の取り扱い
- 製品固有機能への依存と将来の移行費用

## Zero-ETLでも運用責任はなくならない

業務DBからDWHへデータを移す処理は、ETL（イーティーエル・抽出、変換、格納）と呼ばれる。項目追加、型変更、再実行、遅延監視などが必要になり、分析基盤の運用コストになりやすい。

Zero-ETLは、この連携をサービス側で管理し、個別のデータ移行処理を減らす考え方である。たとえばAWSはAuroraやRDSなどのデータをRedshiftへ複製する連携を提供している。

しかし、Zero-ETLは「設計も管理も不要」という意味ではない。次の判断は残る。

- どの表と列を連携するか
- 削除や更新を履歴としてどう扱うか
- 個人情報を分析側へ複製してよいか
- 反映遅延をどこまで許容するか
- 元DBの仕様変更をどう検知するか
- 集計値の正しさを誰が確認するか

転送処理が自動化されても、データの意味と品質までは自動で決まらない。

## DWHだけで注文や決済を動かさない理由

現在のDWHにも、トランザクションや整合性を守る機能を持つ製品はある。そのため「DWHにはACID特性がないから使えない」と一律に説明するのは正確ではない。

それでも注文、決済、在庫引当の主DBとして通常のDWHを選びにくいのは、高頻度な少数行の更新、短い応答時間、多数利用者の同時処理より、大量読み取りと集計に最適化されているからだ。

最終的には製品名ではなく、必要な応答時間、同時更新数、障害時の復旧、整合性保証、費用を基準に判断する。分析と業務処理の境界を扱える製品が増えても、負荷と責任を分けて考える必要はなくならない。

## AI時代には「検索できる」だけでなく「信用できる」ことが必要

AIに「先月の売上低下の原因を説明して」と依頼しても、参照データの定義が部署ごとに違い、欠損があり、過去履歴も残っていなければ、もっともらしい誤答を返す可能性がある。

DWHは、AIが参照する会社の記憶基盤にもなり得る。ただし、DWHを用意すればAIの回答が自動的に正しくなるわけではない。

AI利用前に確認したいことは次の通りである。

- 指標の定義と集計条件が記録されているか
- 元データと集計結果をたどれるか
- 更新日時とデータの対象期間が分かるか
- AIが参照してよい範囲を権限で制御できるか
- 回答の根拠となった表、期間、条件を表示できるか
- 人が結果を確認し、業務判断の責任を持てるか

AI活用のボトルネックは、モデル性能だけではない。過去データを比較可能な形で残し、意味と品質を説明できるかが重要になる。

## 導入、保留、別案の判断

| 状況 | 判断候補 |
| --- | --- |
| 小規模で集計も軽い | 業務DB、集計済みテーブル、定期出力で継続 |
| 分析負荷だけを分けたい | リードレプリカや別の分析DBを検証 |
| 複数システムの履歴と指標を統合したい | DWHを小規模に検証 |
| 定義や管理責任が決まっていない | 構築前に指標、品質、権限の責任者を決める |
| 費用対効果を説明できない | 対象データと利用者を絞り、別案と比較する |

DWHの採用条件は「大量データがあること」だけではない。分析によって改善したい判断があり、そのために必要な履歴、共通定義、運用責任を用意できることが成立条件になる。

## まとめ

業務処理用DBとDWHは、現在と過去、少数行の更新と大量行の集計という異なる仕事を担当する。二つに分けることは目的ではなく、本番業務を守りながら、過去を比較可能な形で残すための設計判断である。

今回の整理で重要だったのは、DWHの価値が単なる高速集計ではない点である。全社のデータ定義と履歴をそろえ、判断の根拠を再現できることに価値がある。

クラウド、列指向、Zero-ETLによって導入の負担は下がっている。一方、指標の定義、データ品質、権限、費用、運用責任は残る。AIにデータを使わせる場合も、まず人がデータの意味と正しさを説明できる状態を作る必要がある。

結論から言うと、受け入れ条件を決めないまま開発すると、画面や機能はできているのに「これで完成と言えるのか」を判断できなくなる。

ボタンがある。エラーも出ない。データも保存できる。

それでも、現場が使えない、入力に時間がかかる、確認者が決まっていない、例外ケースで止まる、AIの結果を誰も承認できないなら、業務としては受け入れにくい。

一方で、画面はシンプルで、機能も必要最低限しかなくても、作業時間が減り、ミスが減り、担当者が迷わず確認できるなら、十分に受け入れられる場合がある。

受け入れ条件は、「開発が終わったか」だけを見るものではない。

約束した価値を提供できているかを確認するための条件である。

この記事では、システム開発で受け入れ条件を決めないまま進めると何が起きるのか、何を先に確認しておくとよいのかを整理する。

PoC、要件定義、検収、責任分界点、CRUDなどの用語は [開発・クラウド・CADの記事で使う用語メモ](/notes/system-development-terms) に短く整理している。

## 受け入れ条件とは何か

受け入れ条件とは、作ったものを「業務で使える状態」として受け入れるための確認条件である。

たとえば、単に「検索機能を作る」だけでは、完成判断が曖昧になる。

次のように書くと、確認しやすくなる。

```text
施設名、地域、公開状態で検索できる。
1000件程度のデータで、通常の検索は数秒以内に結果が返る。
検索結果には、施設名、住所、更新日、公開状態を表示する。
業務担当者が、月次更新作業で必要な施設を探せることを確認する。
```

ここまで決めると、開発者は何を作るべきか分かりやすくなる。業務側も、何を見て受け入れるのかを確認しやすくなる。

受け入れ条件は、細かい仕様をすべて固定するためのものではない。

完成判断の基準を、関係者が共有するためのものだ。

## 機能があることと価値が出ていることは違う

開発中は、機能単位で話が進みやすい。

- 登録画面を作る
- 編集画面を作る
- 検索機能を付ける
- CSV出力を作る
- AIで分類する
- 承認フローを作る

これらは必要な作業である。

しかし、機能があることと、業務上の価値が出ていることは違う。

たとえば、登録画面があっても、入力項目が多すぎて現場が使わないなら、業務改善にはつながりにくい。検索機能があっても、必要な情報が検索対象に入っていなければ、探す手間は減らない。AI分類があっても、誤分類時に誰が確認するか決まっていなければ、業務判断には使いにくい。

逆に、最初の画面は簡素でも、今まで30分かかっていた確認作業が10分で済むなら価値がある。自動化の範囲が狭くても、ミスが起きやすい転記だけを減らせるなら採用する意味がある。

受け入れ条件では、「機能が存在するか」だけでなく、「その機能で何が軽くなるのか」を確認したい。

## 受け入れ条件がないと完成判断が人によって変わる

受け入れ条件がないと、開発者、業務担当者、管理者で完成の見方がずれやすい。

たとえば、次のような状態になる。

| 立場 | 完成したように見える理由 | まだ不安が残る理由 |
| --- | --- | --- |
| 開発者 | 仕様に書かれた画面と機能を作った | 実データや業務例外で確認できていない |
| 業務担当者 | 画面は触れる | 普段の作業を最後まで通せるか分からない |
| 管理者 | デモでは動いた | 運用担当、費用、責任範囲が決まっていない |
| 利用者 | 入力はできる | 失敗したときにどうすればよいか分からない |

このずれは、誰かが悪いという話ではない。

見ているものが違うために起きる。

開発者は機能、データ構造、エラー、性能を見ている。業務担当者は作業の流れ、確認、例外対応を見ている。管理者は費用、責任、運用、社内説明を見ている。

受け入れ条件は、この違いを早めに見える形にするために必要になる。

## 確認データを決めないと都合のよいデータだけで判断してしまう

受け入れ条件で重要なのは、どのデータで確認するかである。

開発中のサンプルデータでは問題なく動いても、本番に近いデータを入れると問題が出ることがある。

たとえば、次のような違いだ。

- サンプルでは10件だが、本番では数万件ある
- サンプルでは名前が短いが、本番では長い名称や旧字がある
- サンプルでは必須項目が埋まっているが、本番では空欄がある
- サンプルでは画像が軽いが、本番では大きなファイルが混ざる
- サンプルでは通常パターンだけだが、本番では例外パターンが多い

この状態で「動きました」と言っても、本番導入の判断材料としては弱い。

受け入れ条件には、確認データの条件も含めたい。

```text
本番に近い件数のデータで確認する。
旧字、長い名称、空欄、重複、過去データを含める。
よくある例外ケースを業務担当者が3件以上用意する。
```

実データを使えない場合でも、本番で起こりそうな形に近いテストデータを用意する価値がある。

この点は [日本語データを扱うシステム開発で確認したいこと](/reports/japanese-text-encoding-system-development) とも関係する。

## 例外ケースを決めないと通常処理だけで完成してしまう

業務システムでは、通常処理だけでなく例外ケースが問題になりやすい。

たとえば、次のようなケースがある。

- 入力途中で保存したい
- 間違って登録したデータを直したい
- 削除してよいか判断できない
- 承認者が休みで処理が止まる
- 外部APIが止まっている
- AIの分類結果が明らかにおかしい
- CSVの列名や文字コードが想定と違う
- 同じ顧客や施設が重複して登録されている

通常処理だけを見れば、システムは完成しているように見える。

しかし、実際の業務では例外が起きる。

受け入れ条件では、すべての例外を最初から完璧に扱う必要はない。ただし、よく起きる例外と、起きたときの対応方針は決めておきたい。

| 例外 | 受け入れ前に決めたいこと |
| --- | --- |
| 入力ミス | 誰が修正できるか、履歴を残すか |
| 重複データ | 統合するのか、警告だけ出すのか |
| 承認者不在 | 代理承認を認めるか、保留にするか |
| 外部サービス停止 | 手動運用に切り替えるか、処理を止めるか |
| AI誤判定 | 候補扱いにするか、人間の確認を必須にするか |
| 削除 | 完全削除するか、非表示や論理削除にするか |

ここを決めないと、開発者は実装上の都合で処理を決めるしかなくなる。業務側は、運用が始まってから「この場合はどうするのか」と困ることになる。

## 誰が確認するかを決めないと判断が止まる

受け入れ条件は、確認項目だけでは足りない。

誰が確認するかも決める必要がある。

開発者は、システムが仕様どおり動くかを確認できる。しかし、業務上それでよいかは、業務担当者や管理者が確認する必要がある。

たとえば、次のように分けられる。

| 確認項目 | 主に確認する人 |
| --- | --- |
| 画面が表示されるか | 開発者 |
| 登録、編集、検索が動くか | 開発者 |
| 実際の業務手順に合っているか | 業務担当者 |
| 公開してよい情報か | 業務責任者 |
| AIの候補を採用してよいか | 業務担当者または管理者 |
| 障害時に手動運用へ切り替えられるか | 運用担当者、管理者 |
| 検収として受け入れるか | 発注側の責任者 |

誰が確認するかが決まっていないと、最後に判断が止まりやすい。

「開発者が確認していると思っていた」「業務側が見ると思っていた」「管理者の承認が必要だとは思っていなかった」というすれ違いが起きる。

この点は [技術者が決めることと業務担当者が決めること](/reports/engineer-business-decision-boundary) とつながる。

## PoCと本番導入では受け入れ条件が変わる

小さな検証では、受け入れ条件を軽くしてよい場合がある。

PoC（ポック・小規模検証）の目的は、最初から本番品質のシステムを作ることではなく、技術的に成立しそうか、どこに制約があるかを早く見ることだからだ。

たとえば、PoCでは次のような条件でもよい。

```text
代表的なデータ10件で処理できる。
主要な入力項目だけを扱う。
担当者が手元で結果を確認できる。
本番導入前に、性能、権限、ログ、バックアップを追加確認する。
```

一方で、本番導入では条件が変わる。

```text
本番相当の件数で処理できる。
権限管理がある。
変更履歴が残る。
障害時の対応手順がある。
業務担当者が確認し、責任者が承認する。
```

PoCの受け入れ条件と、本番導入の受け入れ条件を混ぜると危ない。

PoCで動いたことを、そのまま本番で受け入れられると考えてしまうためだ。

この点は [小さな検証（PoC）が成功しても本番導入できない理由](/reports/poc-success-production-adoption-risks) にも整理している。

## AIを使う場合は「候補」と「確定」を分ける

AIを使うシステムでは、受け入れ条件をさらに丁寧に決めたい。

AIは、分類、要約、文章案、回答候補、コード、画像、抽出結果などを出せる。

しかし、AIが出したものをそのまま確定値として扱ってよいかは別問題である。

受け入れ条件では、次の点を決めておきたい。

- AIの出力は候補なのか、確定値なのか
- 人間の確認を必須にするか
- 誤った出力が出たとき誰が修正するか
- AIの判断理由や入力情報を記録するか
- 外部AIサービスへ送ってよいデータか
- 精度が低い場合は、どこで止めるか

たとえば、問い合わせをAIで分類する場合でも、最初から自動処理にする必要はない。

```text
AIは分類候補を表示する。
業務担当者が確認して確定する。
確定前の分類結果は利用者へ表示しない。
誤分類が多いカテゴリは自動処理対象から外す。
```

このように決めると、AIを使いながらも、業務判断を人間側に残せる。

AIの導入では、「AIが答えを出せるか」だけでなく、「その答えを誰が受け入れるか」を決める必要がある。

この点は [AIがコードを書く時代に人間は何を確認するのか](/reports/ai-code-generation-human-checkpoints) や [AIに専門業務を教える前に確認したい学習データの問題](/reports/ai-training-data-for-specialized-work) とも関係する。

## 仕様変更と追加要望の境界も決めやすくなる

受け入れ条件があると、仕様変更や追加要望の境界も整理しやすくなる。

開発の終盤では、実際に画面を見てから新しい要望が出ることがある。

- この項目も検索したい
- この一覧にもCSV出力がほしい
- 承認後に通知したい
- スマートフォンでも同じ操作をしたい
- AIの判定理由も表示したい

これらは悪い要望ではない。

実際に触って初めて気づくことも多い。

ただし、最初の受け入れ条件に含まれていたものか、追加で検討するものかは分けた方がよい。

受け入れ条件がないと、すべてが「まだ完成していない理由」になりやすい。

受け入れ条件があると、次のように整理できる。

| 要望 | 扱い方 |
| --- | --- |
| 受け入れ条件に含まれる不備 | 修正対象 |
| 受け入れ条件の確認で見つかった重大な問題 | 優先して対応 |
| 目的には合うが当初範囲にない改善 | 追加要望として見積もる |
| あると便利だが必須ではない機能 | 次フェーズ候補 |
| 業務ルール自体の変更 | 業務側で再判断する |

この整理は、開発側を守るためだけではない。

発注側にとっても、どこまでが今回の完成条件で、どこからが追加投資なのかを説明しやすくなる。

## 受け入れ条件に入れたい項目

受け入れ条件を作るときは、少なくとも次の点を確認したい。

| 観点 | 確認したいこと |
| --- | --- |
| 目的 | 何を軽くする、何を減らす、何を判断しやすくするのか |
| 利用者 | 誰が使うのか、どの頻度で使うのか |
| 業務手順 | 実際の作業を最初から最後まで通せるか |
| 確認データ | どの件数、どの種類、どの例外を含めて見るか |
| 例外ケース | 入力ミス、重複、削除、承認者不在、外部停止をどう扱うか |
| 権限 | 誰が閲覧、登録、編集、削除、承認できるか |
| 責任 | 誰が確認し、誰が承認し、誰が運用するか |
| 性能 | どの程度の件数や時間なら業務上許容できるか |
| ログ | 変更履歴、承認履歴、AI出力を残す必要があるか |
| 障害時 | 止まったときに手動運用や代替手段があるか |
| 範囲外 | 今回やらないこと、次フェーズに回すことは何か |

すべてを最初から詳細に決める必要はない。

しかし、未定の項目は「未定」として残した方がよい。

未定であることが見えていれば、追加確認、保留、範囲縮小、次フェーズ化を判断できる。

## 書き方の例

受け入れ条件は、難しい文章にする必要はない。

次のような形で十分に役立つ。

```text
目的:
施設情報の更新を、エンジニアに依頼せず業務担当者が行えるようにする。

受け入れ条件:
- 業務担当者が施設情報を登録、編集、非公開にできる
- 公開前に管理者が内容を確認できる
- 変更履歴として、更新者、更新日時、変更内容が残る
- 既存データ1000件を取り込んだ状態で検索できる
- 旧字、長い施設名、住所の空欄を含むデータで確認する
- 誤って公開した場合に、非公開へ戻せる

今回の範囲外:
- 多言語対応
- 外部予約システムとの連携
- AIによる自動文章生成
```

このように書くと、何を作るかだけでなく、何を確認したら受け入れられるかが分かる。

開発途中で新しい要望が出ても、今回の受け入れ条件に入れるのか、次フェーズに回すのかを相談しやすくなる。

## 受け入れ条件は開発を止めるためのものではない

受け入れ条件という言葉は、厳しく検査するためのものに聞こえるかもしれない。

しかし、本来は開発を止めるためではなく、進めやすくするためのものだ。

受け入れ条件があると、開発者は優先順位を判断しやすくなる。業務担当者は何を確認すればよいか分かる。管理者は費用や運用の判断を説明しやすくなる。

特に不確実性が高い開発では、最初から完璧な仕様を作ることは難しい。

だからこそ、次のように分ける必要がある。

- 今回必ず確認すること
- 分かったら進めること
- 未確認として残すこと
- 次フェーズに回すこと
- 条件を満たせなければ止めること

この整理があると、開発は単なる作業ではなく、判断材料を増やす活動になる。

## まとめ

受け入れ条件を決めないまま開発すると、機能はできているのに、完成したと言えるか判断できなくなる。

大事なのは、ボタンがあるか、エラーが出ないかだけではない。

約束した価値を提供できているか。業務担当者が使えるか。確認データは本番に近いか。例外ケースを扱えるか。誰が確認し、誰が承認し、誰が運用するか。

これらを決めておくと、開発者、業務担当者、管理者が同じ基準で話しやすくなる。

受け入れ条件は、開発を細かく縛るためのものではない。

作ったものを業務で受け入れられる状態にするための判断材料である。
